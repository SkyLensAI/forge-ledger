信任边界进闸门：用一台敌意模型当长期探针（E7）

问题

Phase 4 的退出条件写的是"抽取精确率/召回率达标，且连续 3 天稳定"。 但这句话里藏着一个空洞：分数不是信任边界的判据。

一个类型都对、标题像人话、置信度拉满、出处全是编的实现，分数可能很好看， 而它每一条都不可复核。这是本产品最贵的失败模式——"自信地错" （implement1.md §3.1：过期的事实比没有事实更糟）。Phase 3 的 E4 （"换成永远返回空的实现，它还会及格吗"）分得开活的和死的，但它分不开 "对的"和"听起来对但出处是编的"。

于是问题变成："边界还连着吗"这件事，由谁、多久问一次？

考虑过的选项

  1. 写在文档里（"记得校验出处"）。R8 明确禁止：用自然语言提示代替代码强制。
  2. 只做单元测试。 packages/core/test/ 里已经有 sanitize 与 guard 的用例， 但它们是逐条测的：每加一条判据就补一条用例，而"判据之间的组合有没有漏" 没有人问。更实际的问题是：单元测试跟着实现走，实现被改松时，测试常常跟着一起改。
  3. **在闸门里放一条断言"抽取器必须过 judgeCandidates"。 那是被测者的问题，不是边界**的问题——它测的是这一次抽取的产出， 而边界坏掉的表现是"某一天某一种输入下漏了"。
  4. 一台敌意模型当探针：每次 CI 都让它走一遍完整的真实路径 （渲染请求 → 答 → 解析 → sanitize → 守卫），然后要求四条性质同时成立。

选定

选 4，落成 E7_EVAL_TRUST_BOUNDARY_OPEN。

探针（evals/extractors/hostile.ts）是一台 Model 而不是一台 Extractor， 这是有意的：走 Extractor 就等于绕过了 parseExtractionResponse 与 sanitizeCandidates，而探针要测的恰恰是那条路径。假装成模型，才能真的经过所有检查。

它一次吐出七条，五类敌意各对应一条判据：编造的事件键、file:// 出处、 自造的类型、空标题、置信度写成字符串；外加一条看起来完全合法的 （真键、真类型、置信度 1.0）和一条与它一字不差的重复。

判定的四条性质，缺一条这次检查就不成立：

  1. sanitize 的产出必须过得了 judgeCandidates（边界不许有第二套标准）。
  2. 零条编造出处的候选活下来。
  3. 守卫的 admit 名单里零条模型产出。
  4. 至少一条候选活着穿过 sanitize 并进了候选区。

第 4 条是最容易漏、也最要紧的一条：一个"什么都不放行"的实现能让前三条全绿， 而它显然不是一条好的边界。只会变绿的检查不是检查（R8）。

判定住在 evals/runner/gate.ts（不受保护），所以它能在落盘之前被测试—— 含两条变异用例：把 sanitize 换成什么都不裁的、把守卫换成什么都放行的， 探针必须报红。这是 ADR-0020 那条分工的延续。

后果

  • 好：Phase 4 的退出条件从"分数达标"变成了"分数达标 且 边界连着"， 而且后者是每次 CI 都问一遍的。
  • 好：探针测的是组合（parse → sanitize → judge → guard）， 而不是逐条判据——逐条用例盖不住的那部分正好是它盖的。
  • 好：探针是一台 Model，所以它顺带把 buildExtractionRequest 的渲染、 代码块剥离、字段读取这几段也钉住了（它们此前只有逐条用例）。
  • 好：把探针结果放进 EvalReport 而不是做成一个独立入口。 独立入口会被人忘掉，而"忘了调它"与"调了它是绿的"在闸门上长得一模一样。
  • 代价：每次 runEval 多跑一次（消耗是微秒级），以及 EvalReport 多一个字段。
  • 代价：探针的七条产出是写死的。一个新发明的敌意手法不会被它覆盖， 除非有人往 hostile.ts 里加一条。缓解是那台模型的文件头按"哪一条对应哪条判据" 逐条列出来——加一条的门槛很低，而低了才会有人加。
  • 残余风险：探针的敌意是想象出来的。真实模型编造出处的方式（例如把两段 来源的键混起来、或者用近似的键名）未必是这七条。真正的覆盖来自把真实失败案例 放进 evals/regressions/——那需要先有真实运行，而本仓库还没有 key。
  • 残余风险：E7 只检查"边界在这一台敌意模型上连着"。它不证明边界在 任意模型上连着。这是抽样，不是证明——记在这里，不写成"信任边界已被证明"。
