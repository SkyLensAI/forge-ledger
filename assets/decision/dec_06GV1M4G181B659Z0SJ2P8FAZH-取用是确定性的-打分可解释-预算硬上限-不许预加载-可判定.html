取用是确定性的：打分可解释、预算硬上限、"不许预加载"可判定

问题

S21 的一句话是"Retriever + 注入预算控制；绝不预加载全库"。 把它落成代码时有四个坑，每一个都能让这句话在某次"优化检索质量"里失效：

  1. "相关性"变成一个说不清的数字。 一旦换成 embedding 或相似度阈值， "为什么这条进来了"就再也回答不了——而不知道它为什么进来正是 context rot 的起点 （implement1.md 把它写成不能让步的运行时决策之一）。
  2. 预算是软的。 "还差一点点，就多塞一条吧"每一次都很合理， 而后果在使用方那一侧：窗口被静默吃掉一截。这类失败没有响声。
  3. "不预加载"没有判据。 一个把全库倒进去的实现，只要预算够大，就全程绿灯—— implement2.md 把"注入预算"列为 P6 的 CI 强制项，而只查预算等于只查了一半。
  4. 过期的东西被当成现状注入。 库里留着被取代的那一代（ADR-0028 刻意留着，为了可追溯）， 把它注进模型就是把"过期的事实"喂出去——比没有事实更糟。

考虑过的选项

  1. 用向量检索。 质量可能更好，但打分不再可解释、不可快照、还要引入一个模型依赖 （"没有 API key 也能跑通全链路"当场失效）。而且质量不是现在的问题—— 信任才是。
  2. 预算只当提示词里的一句建议。 那就是把判据交给礼貌。
  3. 打分 = 词法命中 × 类型权重；预算 = 渲染出来的整块 token 数 ≤ 上限； 预加载 = 注入里出现分数为 0 的条目。 三条判据都是纯函数、可复现、可在没有 key 的机器上跑。
  4. 新鲜度参与排序（越新越靠前）。多一个因子就多一个说不清的地方， 而"过期的根本不进"已经是一个足够强的判据。

选定

选 3，外加"新鲜度只决定进不进、不决定排序"。 逐条落到代码里：

  1. 打分可解释：score = Σ 词法命中 × 字段权重 × 类型权重，每一项都进 why （闸门（题面 ×1 · 正文 ×2））。字段权重（题面 6 / 标题 4 / 正文 2 / 出处 1） 与类型权重（rule 1.4 / decision 1.2 / state 1.1 / event 0.8）都是显式常量， 所以"为什么规则排在前面"是能指着说的。
  2. 预算是硬上限：量的是渲染出来的整块（含"这不是全库"那几行元信息）， 不成立就从末尾退条目。退让的方向有讲究：末尾是排序里最不相关的那条。
  3. "不预加载"可判定：注入的每一条分数必须大于 0。 与被排除的条数、被预算挡住的条数一起写在注入块自己里面—— 它会被人原样贴到别处去，而一句留在 CLI 报告里的说明不会跟着走。
  4. 过期不当现状：superseded / retired 与超出新鲜度窗口的 state 根本不进候选，进 excluded 并说出原因。不给基准日 = 没有校验新鲜度， 不是"都新鲜"（ADR-0009 的同一个区分）。
  5. 出处是硬约束：没有 span 的条目不进注入，而且这一侧再判一次—— 闸门可以被绕过、旧资产可能写在闸门存在之前，而注进模型的每一句话都要能被点开。

闸门里那两条检查（P6 的 CI 强制项）：

  • E10_EVAL_INJECTION_BUDGET：拿本仓库自己的 29 条资产当语料，用它们的标题当查询， 要求每一块都不超预算；并且探针自己不许瞎（所有查询一条都不注入、 或每个查询都把整个库判成"有关"，都算瞎——一个"什么都不给"的实现能让预算检查全绿）。
  • E11_EVAL_PRELOAD：对照查询（ASCII 乱码，绝无命中）必须一条都不注入； 任一查询的注入条数不得超过语料的 50%。 它必须与 E10 分开：预加载不会让预算检查变红。

两条都用真实语料（自己的库），不用手编的玩具集——手编的查询会逐渐变成 "为当前实现量身的查询"（与 ADR-0020 那条"尺子要有人确认"同源）。

后果

  • 好：整个取用路径零模型、零 IO、零时钟（today 由调用方注入）， 所以它可以被快照、被 diff，也能在没有 API key 的机器上跑。
  • 好：三个宿主（CLI / MCP / 浏览器桥）走的是同一个入口（vault.context()）， 测试里逐字节断言它们输出相同——"为什么命令行里看到的和 Cursor 里看到的不一样" 这个问题在结构上不会出现。
  • 代价：词法检索会漏掉改写过的相关内容。它比语义检索差， 而"差一点但可解释"在这里是刻意选的那一边。
  • 代价：注入的是线索不是全文（MAX_ITEM_CHARS = 320）。 代价由"按需取全文"补偿（forge_get / 路径 / 点开文件）。
  • 实测的参数：MIN_BUDGET_TOKENS = 600 是被逼出来的，不是拍的。 探针一开始用 240，结果每一个查询都是"0 条注入"——元信息把预算吃光了。 那是"预算内"没错，但那不是取用。换成真实语料（29 条 ADR）之后 480 也不够， 于是同时把 MAX_ITEM_CHARS 收到 320："装不下"的信号先指向条目太大， 而不是预算太小。
  • 残余风险：中文走二元组切分，字符级碰撞会让"无关"变成"看起来无关"—— 探针第一版的对照查询「企鹅的迁徙路线与南极冰盖」命中了 2 条 ADR，因为库里有一条 写着「……的迁移……」。这不是缺陷（二元组就是这个代价），但它说明对照查询 不能用自然语言。记在这里，不假装它不存在。
