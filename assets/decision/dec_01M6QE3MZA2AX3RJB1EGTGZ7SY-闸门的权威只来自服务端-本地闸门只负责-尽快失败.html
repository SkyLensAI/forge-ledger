闸门的权威只来自服务端；本地闸门只负责"尽快失败"

问题

要装五道闸门（agent hook / pre-commit / required status check / branch rule / 发布门），但每一道都有不同的绕过方式：改 hook 配置、--no-verify、管理员豁免、本机手动发布。如果把它们当成"五道平等的防线"，会得到一个危险的错觉——以为本地绿水等于合规。

考虑过的选项

  1. 只装本地钩子（最快、零配置）。但 agent 或人都能一条 --no-verify 跳过，等于没装。
  2. 只装 CI。判定可靠，但反馈要等一个 CI 周期，人会在等待中失去耐心，进而开始绕过。
  3. 分层：本地做早期反馈，服务端做权威判定，两层用同一套判定代码。

选定

选 3。

  • 判定逻辑只有一份：scripts/gates/lib/policy.mjs（纯函数、零 IO）。闸门 2 与闸门 3 调的是同一个 evaluateChangeset。
  • 权威只在服务端：本地闸门全部可绕过，因此它们的存在意义是"不要等到 CI 才知道错"，而不是"拦住"。
  • 推论：--no-verify 跳过 pre-commit 是可以接受的（它是已知绕过方式），只要 CI 用同一套策略重判一次——这正是它无法被跳过的地方。
  • 推论：CI 还必须检查闸门本身是否完整（scripts/gates/lib/harness.mjs）。否则"删掉检查"就成了最省事的绕过方式。

后果

  • 好：本地反馈快，服务端判定硬；绕过本地闸门不会导致不合规的代码进入 main。
  • 好：判定代码只有一份，不会出现"本地过了 CI 挂"的漂移。
  • 代价：CI 成为单点，必须保持快（当前只有 lint/typecheck/test + 两个纯函数判定）。
  • 代价：pnpm install 之前本地闸门是静默失效的（core.hooksPath 未设置）。这一点不假装解决，记录在 docs/gates/bypass-matrix.md。
