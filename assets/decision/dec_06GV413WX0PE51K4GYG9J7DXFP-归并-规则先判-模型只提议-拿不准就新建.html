归并：规则先判，模型只提议；拿不准就新建

问题

S18 的判据只有一句：规则优先，LLM 只判"这两条是不是同一件事"；不确定就新建，别乱并。 难点在于把它写成两件互不越权的事——而"谁说了算"这个问题在归并上比在抽取上更尖锐：

抽取判错了，代价是候选区里多一条垃圾（人还能拒）。归并判错了，代价是把两条 本来分开的事实合成一条：证据混在一起、正文互相覆盖，而没有任何东西会因此变红。 它是本产品最安静的失败模式。

还有一条不能丢的性质：归并是"分组"，不是"覆盖"。 把一条候选并进一个已有实体， 不该改写那个实体的任何一个字节——改写是"冲突处理"（S19/S20）的事， 而那条路上有人。

考虑过的选项

  1. 全交给模型判。 让 LLM 对每一对候选说"是不是同一件事"，是同一件事就并。 最省事，也最危险：模型说"是"的代价是不可逆的合并， 而一个总是说"是"的模型能让整个库塌成一个实体——它还很难被发现， 因为合并后的库看起来"更干净"。
  2. 全靠规则（题面归一化相等 + 证据相同）。 完全可解释、可复现， 但必然漏：模型抽出来的题面是自由文本，数据库的存储层 与 存储层选型 说的是同一件事，字符串函数看不出来。
  3. 规则优先 + 模型提议，两条路都不许改写任何东西。 规则能证的（同一处证据、同一个归一化题面）→ 直接链接到同一个实体； 模型认为可能是同一件事的 → 提议，进冲突/归并队列等人确认。
  4. 干脆不归并，每条候选都新建一个实体。零风险，但库里会长出 同一件事的十几条记录，而"这件事现在是什么样"变成一个检索问题而不是一条断言。

选定

选 3。 三条路，各有各的判定者和各自的落点：

| 判据 | 谁判 | 结论 | 落点 |
|---|---|---|---|
| 证据完全相同（同类型 + 同一组 span） | 代码（确定性） | 同一件事 | 直接链接 |
| 归一化题面相同（`<类型>#<题面>`） | 代码（确定性） | 同一个实体 | 直接链接 |
| 题面不同，但**可能**是同一件事 | 模型（提议） | 拿不准 | 队列，等人 |
| 其余 | —— | **新建** | 直接新建 |

四条设计决定：

  1. 题面键带上类型。 state#数据库的存储层 与 event#数据库的存储层 不是同一个实体——写规则不同的东西不该被并到一起（ADR-0006 的同一条理由： 切法按写规则）。把类型并进键里，这条边界就由键的形状保证，不靠调用方记得。
  2. 归一化只折叠排版。 NFKC、折叠空白、折叠大小写、剥掉包裹的标点、 限长 60 字符（超了不是题面，是一句话）。不做同义词： 数据库 与 存储层 归一化之后仍是两个键，它们要并起来得走模型提议那条路。 这条限制让"直接链接"这件事永远可以被一个字符串函数复核。
  3. 模型的提议永远只是提议。 提议的输出类型里没有"已应用"这一档， 它也进不了 links 名单——自证函数 proposedMergesApplied() 会在有模型提议 混进直接链接时返回非空（packages/core/test/link.test.ts 里有一条变异用例钉住它）。 为什么不给模型一个"高置信度就直接并"的口子：那个口子的阈值会被调， 而"并错了"是不可逆的——与 ADR-0022 不给守卫留"模型可以直接入库"的旋钮是同一条理由。
  4. "拿不准"的默认方向是新建，而不是并。 归并的假阴性只是库里多一条， 假阳性是两条事实被压成一条而且看不出来。两个方向的代价不对称， 所以默认值取便宜的那一边。

后果

  • 好：归并的每一条结论都能被指着解释：要么"同一处证据"，要么"同一个归一化题面", 要么"模型提的，人在队列里点了头"。没有第四种。
  • 好：forge link 在没有任何模型的情况下也能跑，而且能跑出结果—— 同一处证据被抽两次、题面一模一样的候选会被并成一个实体。 这是"无 API key 也能跑通全链路"（implement1.md §4）在 P5 这一环的兑现。
  • 好：链接不改写任何字节，所以归并的 bug 最坏情况是"实体分得太细"， 而不是"某条事实被悄悄改写"。数据被改写只发生在两处：promote（人触发） 与冲突的 resolve（人触发）。
  • 代价：模型提议要人工过一遍队列。这是有意的成本， 它也正是"维护型产品"愿意付费的那个动作（implement2.md 把冲突队列标成收费点）。
  • 代价：同义题面会漏并，于是同一个实体可能同时存在两条 state—— 而它们之间的"矛盾"也不会被报出来（因为题面键不同，两条都不是彼此的候选）。 这条缺口写在 docs/handbook/conflicts.md 里，不假装它被解决了。
  • 残余风险：归一化折叠了大小写，于是 Postgres 与 postgres 是同一个题面。 折叠的理由是"同一件事的两种写法"，风险是"确实靠大小写区分的两个东西" （比如两个同名但不同的环境）会被并起来。这一条没有额外代价： 归并不落盘任何东西（它是每次运行现算的一张视图，像索引层一样可重建）， 并错了只影响这一次报告里的分组，库里一个字节都没动。
