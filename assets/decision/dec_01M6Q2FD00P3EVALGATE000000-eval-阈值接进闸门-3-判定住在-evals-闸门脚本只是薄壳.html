eval 阈值接进闸门 3；判定住在 evals/，闸门脚本只是薄壳

问题

Phase 3 的交付物是三样：eval runner + 20 条人工确认的黄金集（S12）、 不变量测试（S13）、CI 接阈值，红了不许合（S14）。 退出条件写得很具体：把 Extractor 换成一个"永远返回空"的假实现，CI 必须变红。

要落这三样，必须动 scripts/gates/（受保护路径，R2/R3）。而这里有两个不显然的问题：

  1. 判定写在哪儿？ assets.mjs / consistency.mjs 的先例是"判定住 packages/core， 宿主只做编排"。但 eval 闸门的判定不属于产品逻辑——它是闸门的判定。 塞进 packages/core 会让产品包里长出一段只有 CI 用得到的东西。
  2. 谁来测这段判定？ 闸门本体是受保护路径，agent 写不了，只能由人落盘。 如果判定写在闸门脚本里，那它要等落盘之后才第一次被执行—— "闸门第一次运行"就发生在它生效的那一刻，那不是演练，那是赌博。 这个仓库恰好有一条明文纪律反对这件事（Phase 0 的洞是靠演练发现的，不是靠读代码）。

考虑过的选项

  1. **判定写在 scripts/gates/evals.mjs 里**（和 assets.mjs 一样厚）。 简单，但它在落盘之前一行都跑不到；而且它把"判定"和"受保护"绑在一起， 于是每次调阈值语义都要走一遍人工落盘。
  2. **判定塞进 packages/core**。能测，但产品包里会长出一段 "只有 CI 关心"的逻辑，而 core 的定位是"零 IO 的编译与维护引擎"（R5）。
  3. **判定住 evals/runner/gate.ts（不受保护），scripts/gates/evals.mjs 只做薄壳** （读 node_modules、跑 runner、调判定、设退出码）。
  4. 干脆不要这道闸门，只把 eval runner 留着让人手动跑。 这正是 implement1.md 反模式 3（"没有 eval 就说效果不错"）的近亲—— 一条不接进任何强制通道的尺子，等于一条没人看的报告。

选定

选 3。

  • 判定的归属由"谁能测它"决定，而不是由"它看起来像什么"决定。 把判定放在不受保护的 evals/runner/gate.ts，它就和其他所有代码一样， 在落盘之前就能被 pnpm test 跑、被变异用例钉住。 薄壳里只剩下编排与退出码——那部分必须等落盘才能验，而它是十行。 这不是把闸门藏到不受保护的地方：薄壳一旦被删，G3_EVAL_GATE_MISSING 会红（见下）。
  • 判定的码表跟着判定走。 E1–E6 定义在 evals/runner/gate.ts， 而一致性检查（C4）扫的也是这份文件——扫"判定实际所在的那份"， 不是扫薄壳。薄壳里没有码可扫。
  • 阈值是地板，不是目标。 它回答"实现是不是坏掉了"，不回答"实现够好了吗"。 把它当目标是这个项目最舒服的死法：一个刚好卡在阈值上的实现， 配上一群以为自己在被保护的人（implement1.md §2.3）。 所以 evals/thresholds.json 里写死了这句话，实测数字写在 evals/README.md。
  • golden 集与阈值都必须被人工确认，而且由闸门检查。 这不是形式主义：golden 集由 agent 自己写、自己判，就是让模型给自己发合格证， "先有尺子"的意义会整个消失。implement2.md 的人机分工表把 P3 的"人必须做" 明确写成"阈值与 golden 集"。所以闸门里有两条检查（E2 / E6）专门盯这件事。
  • 确认绑在内容指纹上，不绑在文件名上。 只查"有没有人点过头"，留下的是一张能盖在任何后续改动上的橡皮图章—— 包括"agent 事后往 golden 集里塞一条恰好让当前实现变准的用例"。 所以 review.cases_sha256 与 extraction.thresholds_sha256 记的是被确认那一份的 规范化 JSON 哈希，闸门比对的是当前这一份。改一个字节就要重新确认。 用规范化（键递归排序）而不是原样 JSON.stringify：纯排版改动不该让确认失效， 否则只会训练人闭着眼睛重签——那比不签更糟。这与来源层的"内容寻址"是同一条思路 （ADR-0013）：承诺绑在字节上，不绑在名字上。
  • **"尺子还睁着眼吗"是一条独立的检查（E4）。** 阈值可以被慢慢调松、runner 可以被改得永远算满分，而这两种改动都会让 "分数够不够"继续绿。E4 不依赖任何分数：它直接问 "把实现换成永远返回空的那个，它还会及格吗"。这是 Phase 3 的退出条件本身， 写成了一条每次 CI 都跑的检查——退出条件不该只被验证一次。
  • **子闸门需要自己的防拆检查（G3_EVAL_GATE_MISSING）。** 删掉 evals.mjs、或者留着文件但从 ci.mjs 的清单里摘掉它， 不会让任何别的东西变红：lint 照样绿、快照照样绿、测试照样绿。 于是"绿灯"重新退回成"代码看起来还行"的意思，而"需求被满足了吗"重新无人回答—— 这正是 implement1.md §2.3 那句话说的失败模式。

后果

  • 好：闸门的判定在落盘前就被 24 条用例钉住了（含 3 条边界： 空实现及格、召回率恰好等于阈值、只差一点点）。
  • 好：两处"尺子自己的问题"（E5 用例指不回原文、E4 尺子瞎了） 与"被测量者的问题"（E1 分数不够）分开报。混在一起会得到一份 "分数很难看"的报告，而人从那份报告里读不出该去修什么。
  • 好：不变量（S13）每条都配了反例。一条只会变绿的不变量， 与"记得加出处"这种礼貌指令没有区别（R8）。
  • 好：dogfooding 立刻见效——尺子第一次跑就抓到了黄金集自己的两处缺陷 （一条 #t: 锚点只有 7 字符、一条 #k: 指错了 JSON 路径）。 这正是"先审尺子自己"这一步该有的产出。
  • 代价：scripts/gates/ 与 schema/provenance.md 共 5 个文件由人落盘 （handoff/，一条命令）。这是 R2/R3 的既定代价，不是这次的额外开销。
  • 代价：阈值目前只能区分"比一个词法基线还差"与"不比它差"。 它测不出"够不够好"——那是 Phase 4（S17）拿基准报告定的事。 这条限制写在 evals/README.md 的第一段，不留给读者自己发现。
  • 残余风险：E2/E6 检查的是"有人对这一份内容签过字"，不是"那个人真的读了"。 指纹绑得住"改了什么"，绑不住"签的人走没走心"。 这与所有评审类闸门一样，最终落在一个人的判断上。缓解是让确认变便宜—— 每条用例的 why 一行、判据是一个能点开核对到原文的 span。 一次"没看就签"的确认会让尺子退化，而这次的缓解只是降低它的概率。
  • 残余风险：词法基线的分数（精确率 0.882 / 召回率 0.882）是在 同一批人写的用例上量出来的。它足以当前置地板，但不能被读成"抽取质量已达 88%"。 Phase 4 引入真实 trace 反向造的回归集（evals/regressions/）才是对这个数字的检验。
