「schema/ 与 packages/schema 一一对应」必须变成机器可判定的红

问题

directory.md 要求人读的 schema/ 与代码侧的 packages/schema 一一对应，并且"在 CI 里比对一致性"。 但"一致性"如果只由人评审，它就会像所有 checklist 一样被跳过（反模式 4）。 具体哪些一致性是机器能判定的？

考虑过的选项

  1. 只校验 YAML 能被代码解析（结构一致）。
  2. 结构一致 + 可列举的漂移检查：每个违规码必须出现在 schema/provenance.md； 每个 ID 前缀必须出现在 schema/ids.md；每个 requires_fields 必须是代码已知字段； 每个类型的模板必须真的包含它的必填字段与必填章节；新鲜度只许挂在 state 型上。
  3. 文档由代码生成（provenance.md 直接从码表渲染出来，单一来源）。

选定

选 2。

  • 选 3 看起来最彻底，但它把文档降级成产物。这两份文档要讲清为什么有这条规则 （为什么不可解析和没有出处要分开报、为什么外部证据要先落 source 层）—— 那是码表生成不出来的，而"为什么"正是这个产品要卖的东西。
  • 选 2 检查的是漂移，不是正确性。漂移是这两份文档唯一会犯的错： 代码加了码忘了写文档、文档写了前缀分类法里没有、模板漏了必填项。 把它变成红，比"约定要同步更新"这种自然语言提示强（反模式 2）。
  • 一致性判据自己也要被文档化：一致性检查的码必须出现在 docs/handbook/gates.md。 检查者无人审查，就会变成下一个"看起来在保护你"的东西。

后果

  • 好：改代码忘改文档 → CI 红；改文档忘改代码 → CI 红。 "两者必须一一对应"这句话第一次有了执行体，而不是一句设计意图。
  • 好：判据可列举、可测试，每条检查都有正反用例。
  • 代价：加一个违规码要同时改 3 处（码表、provenance.md、测试）。这是有意的耦合—— 码是代码与人之间的契约，契约本来就不该能单方面改。
  • 代价：检查只要求"文档里提到过"，不校验解释得对不对。机器判不了的那一层留给评审， 并且明确记为不覆盖，不假装它被保证了。
  • 残余风险：可列举的检查覆盖不到语义漂移（文档把某条规则解释反了）。 缓解是 R2：schema/ 的改动必须配 ADR，而 ADR 是给人看的。
