规模探针是退出条件的结构性替身，不是退出条件本身

问题

implement2.md 给 P7 写的退出条件是：

库里涨到 500–1000 条事实仍然可用——这是公认的家酿大脑漂移阈值 [14]。

这句话是这一章里最不能靠代码证明的一条。"仍然可用"是一个关于人的判断： 检索得到的那一条是不是真的答了问题、过期的那些有没有被及时看见、 孤儿有没有变成噪音。任何自动化测试都不能替人回答它。

但"不能证明"不等于"什么都做不了"。两个选项：

  1. 什么都不做，在 README 里写一句"未达成"——诚实的记账，但留下了没有见证人的风险；
  2. 把这句话拆成几件能被证伪的事，让它们在 CI 里每次跑一遍。

考虑过的选项

关于做什么：

  1. 造 1000 条语料，量"检索质量"。 否决：语料是合成的， 没有"正确答案"可对，量出来的分数是自娱自乐。
  2. 只量性能（跑得多快、内存多少）。 否决：性能不是这个退出条件的瓶颈—— 1000 条对词法检索来说微不足道。真正会随规模退化的是信号： 一处腐烂混在 1000 条好数据里，还看得见吗？
  3. 量三件能被证伪的事：确定性、信号、边界。 采纳。

关于这三件事各自怎么判：

  • 确定性：同一份 1000 条语料跑两次健康检查与报告渲染，字节必须相同。 规模是"隐式顺序"最喜欢藏身的地方——Object.keys、readdir、Map 的插入顺序 在小语料上碰巧稳定，在大语料上开始分叉。
  • 信号：在 1000 条好数据里埋一处腐烂（"替换写了一半"），必须被找到。 这是"被淹没的清单等于没有清单"那条纪律的规模版。
  • 边界：干净语料上仍然零发现（一个"见到什么都报"的实现能让信号检查全绿）。

关于样本大小：

  1. 用完整的 1000。 采纳。500–1000 是 [14] 给的量级，用下限的一半去测 等于在测另一个问题。1102 条语料的生成与判定在毫秒级——这不是一个需要优化的成本。

选定

  • evals/runner/maintenance.ts 的 runScaleProbe()：造 1002 条语料 （三类资产共享同一处出处），埋一处"替换写了一半"，要求：
  • 健康报告两次字节相同；
  • 那处腐烂被找到；
  • 干净语料（同一次运行里的其它部分）不产生噪音。
  • 闸门码 E14_EVAL_SCALE_DEGRADED，判定在 evals/runner/gate.ts （与其它探针同一条分工：判定住在能被测试的那一侧）。
  • 它不证明"仍然可用"。 README 里 P7 的退出条件那一行会一直写着"未达成"。 探针证明的是"还能用"这句话的地基：机器不崩、产出可复现、信号不被淹。

后果

  • 好：退出条件从一句愿望变成三条可执行的读数。它们红了的时候， "库已经不能用了"这句话至少有一个明确的起点。
  • 好：确定性在规模上第一次被真的问过。ADR-0017 说"排序键显式写死"， 而 1000 条的语料是那句话的检验场。
  • 代价：CI 多几百毫秒。语料是纯内存构造的（不落盘），所以它的成本与 "读一次仓库"同级。
  • 残余风险：合成语料的形状是我自己挑的（三类资产、共享一处出处、 每个题面只出现一次）。真实库的长尾（同一题面几十条、来源上千份）不在它的覆盖里。 换句话说：它防的是"机器在规模上退化"，防不了"真实库的形状让判据失效"。 后者只能靠真实使用来发现——而那正好就是退出条件本身。
