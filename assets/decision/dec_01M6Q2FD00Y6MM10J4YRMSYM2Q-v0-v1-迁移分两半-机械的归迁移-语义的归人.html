v0→v1 迁移分两半：机械的归迁移，语义的归人

问题

ADR-0008 说迁移通道的回归用例不是假数据，而是仓库里那 5 条写在 schema 之前的 ADR （缺 schema_version，sources 是 v0 的自由写法）。

真去迁它们的时候，一条界线浮出来了：其中一部分能用规则转，另一部分不能。

  • 能转：缺 schema_version → 补 1；implement2.md#Phase 0 · S3 → file://docs/implement2.md#t:Phase 0 · S3。
  • 不能转：scripts/gates/rehearse.mjs#场景 A。那个锚点归一化后只有 4 个字符， 在任何文档里都能命中——把它转成一个 #t: 会得到一个"能过闸门"的 span， 但它什么也没定位到。
  • 更不能转：ADR-0005 的 origin_incident 是一整句自由文本 （"Phase 0 演练场景 A：删掉 policy.mjs 后 CI 不是判定为红，而是崩溃"）。 它描述了一次真实事故，但它不是一个能解析的位置。

考虑过的选项

  1. 让迁移"尽力而为"：转不了的按路径猜一个最近的位置写进去。
  2. 让迁移只做能做的，转不了的保留原样并记 note，由人重指。
  3. 先把设计文档改到能被 v0 锚点命中（在 implement2.md 里加上 ## Phase 0 · S3 这样的标题），这样机械转换就全都成立。

选定

选 2。

  • 选 1 是这里唯一真正危险的选项：它产出的假出处能过闸门。 ADR-0009 的立论就是"腐烂的出处比没有出处更糟——它看起来像证据"， 而这个选项会批量制造这种腐烂，还带着"迁移已完成"的背书。
  • 选 3 看着很聪明，其实是让证据去迁就引用：为了让 #h:Phase 0 · S3 命中， 得往设计文档里塞一堆为引用服务的标题。文档的形状会开始被引用格式牵着走， 而下一次改文档的人不会知道那些标题是"为了别人能引用"而存在的。 引用应当指向文档里本来就有的东西。
  • 所以 migrateV0ToV1 返回 {text, notes}：notes 就是"这一条我转不了， 需要一个知道那份文档的人来指"。空的 notes 才代表机械部分全部完成。
  • 落地的分工是：迁移代码负责机械部分（可测试、幂等、有 fixture 回归）， 人负责语义部分（这次是重指 5 条 ADR 的 10 条出处 + 1 条 origin_incident）。 两部分都在同一个变更集里，diff 上分得清哪条是机器写的、哪条是人写的。

后果

  • 好：迁移是纯函数、可测试、幂等（重复跑不会产生第二个 schema_version）。
  • 好：notes 让"迁移跑完了"和"迁移跑完了但有 3 处要人看"是两种不同的输出。 这是 ADR-0009 那条"无法校验 ≠ 校验通过"的同一条原则，用在迁移上。
  • 代价：迁移的第一次真实使用就需要人工介入，所以"迁移是全自动的"这个期待 从一开始就不成立。这是如实反映：资产格式的变更里，总有一部分是语义的。
  • 代价：那 5 条 ADR 的 diff 里混着机器和人的改动。缓解是 ADR-0008 已经写下的规则—— 区间只能机械变换，语义修正在迁移之外单独发生，且这一次被记在这里。
  • 残余风险：notes 是给人看的字符串，没有强制力。一次"人没看 note 就提交"的迁移 会退化成选 1。缓解：迁移不在闸门或 CI 里自动跑（那是"顺手兼容"的温床）， 它是显式命令，输出直接打到终端。
