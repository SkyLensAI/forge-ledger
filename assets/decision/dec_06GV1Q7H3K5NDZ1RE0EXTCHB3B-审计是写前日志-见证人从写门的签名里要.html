审计是写前日志，见证人从写门的签名里要

问题

implement2.md 给 S27 写的是"审计日志 + hook 强制执行，不靠礼貌指令"。三个问题：

  1. "hook" 指哪一个？ 这个仓库有五道闸门，但它们挂在 git 上—— 而用户库在 data/ 里，不在 git 里（R1：用户数据永不进 git）。 也就是说，对一个真实的用户来说，"把审计挂到 pre-commit 上"这件事根本不存在。
  2. 审计记什么？ 全记会把日志灌满（每次 compile 都写几十条派生写入）， 而被刷屏的日志等于没有日志。
  3. 怎么保证"记了"？ 如果 writeAuthored 与 audit.append 是两个可以被拆开的调用， 那就又回到了"记得写"——而 R8 说的正是这件事。

考虑过的选项

关于强制点：

  1. 挂到 git hook 上。 对用户库无效（它不在 git 里）。对本仓库倒是可以， 但那管的是开发流程，不是产品行为——implement2.md 给 P7 写的"审计完整性"是产品侧的。
  2. **在 MCP / forge serve 这些宿主里各记一遍。** 三个宿主三份实现， 而漂移的方向永远是"某个宿主漏记"。这正是 packages/core 存在的理由。
  3. 把审计条目做成写门的必填参数**：writeAuthored(doc, draft)。 采纳。没有见证人，就没有第二条写路径可调**——这不是"记得写"，是签名。

关于记什么：

  1. 全记（含派生的索引写入）。 否决：compile 会写几十条， 真出事时那一条会被淹掉。
  2. 只记不可重建的写入：来源追加、候选落盘、人工确认、冲突判决、重新确认。 采纳。判据与三层存储的判据是同一条（ADR-0015）：能重算的东西不需要记账。

关于误记与漏记之间怎么选：

  1. 写盘成功之后再记审计。 崩在两步之间会留下"改了但没记"—— 那是漏记，而漏记的那条资产从此没有主人，且没人知道它存在。
  2. 先记审计，再写盘（写前日志）。崩在两步之间会留下"记了但没改成"—— 那是多记，看得见（AUDIT_DANGLING_SUBJECT 会把它报出来）。 两个方向的代价不对称，采纳 7。

关于链：

  1. 一个 append-only 的文件就够了。 否决：append-only 是约定。 有人删掉一条、调换两条、把某条的理由改一句话，这三种在纯文本日志里都看不出来—— 而它们恰好是审计唯一要防的事。
  2. 哈希链 + 逐条验证。 采纳。链把"没人动过"从一句承诺变成一次可重算的检查。 哈希不包含它自己（一个哈希不能包含它自己，这是定义）；这一条踩过坑， 见 evals/regressions/0006。

选定

  • 日志住在 <vault>/audit/audit.jsonl：一行一条、只追加、键排序、无时间戳之外的随机。 用 JSONL 不用 SQLite：审计要能被 grep、被编辑器打开、被 git diff—— 索引层可以重建，审计不行，而不可重建的东西不该锁在二进制里。
  • 条目 = {seq, at, actor, kind, subject, detail, prev, hash}。 seq 连续、prev 接前一条的 hash、at 不许倒流。
  • 写前日志：先 audit.append，再写文件。多记看得见，漏记看不见。
  • 强制点在 packages/store 的唯一写门：writeAuthored(doc, draft)。 第二个参数是必填的审计条目，运行时还会再问一遍（类型不是边界）。 顺手**删掉了 writeDerived**：它的调用点是零，而一个没人用的写门摆在 没有见证人的那一侧，就是在等某一天有人用它绕开审计。
  • 时钟在 openVault(root, {now}) 注入（默认 Date.now）：审计条目的时刻是输入， 于是"冻住时间跑两次得到同样的字节"在测试里是一行代码。

必须写下来的边界（不假装堵住了）：

  • 审计挡不住直接改文件系统。 文件系统不会问"你记了吗"。 所以审计做的是让这种写入在健康检查里被看见（AUDIT_UNATTRIBUTED_ASSET）， 而不是"强制每一次写入"。这是记账。
  • 同时写没有锁：两个进程同时跑 promote 会读到同一个链尾。 链的验证会把它报出来，但不会阻止它。单人本地工具可以接受，团队版（Phase 8）加锁。
  • 链断掉之后整份日志都不再可信，包括看起来没问题的条目。 修法是恢复备份或写下"这一段不可追溯"，不是手工调 seq 或重算 hash—— 那是改历史。

后果

  • 好："不靠礼貌指令"有了执行体：探针每次 CI 都试一遍"不给见证人直接写资产"， 要求它抛；再删一行、改一行、换两行，要求三次都被抓住（E12）。
  • 好：用户库第一次有了"这条是谁、什么时候、凭什么变成这样的"这个问题的答案—— 而这句话正是 directory.md 说的那种"别人抄不走的部分"。
  • 代价：每一次写入多一次文件追加与一次全日志读取（append 现读链尾， 不缓存——缓存与被审计的东西住在同一个进程里，改日志的人只要重启一次进程， 缓存就替他把链接回去了）。
  • 代价：审计文件会持续增长，而且没有轮转。轮转要解决"轮转点之前的链怎么办"， 而那是一个新问题；在日志长到难用之前不引入它。记在这里。
  • 残余风险：detail 只收字符串字典。这是为了日志能被 grep 与被打印， 但它意味着结构化的事实（比如一次判决的全部参数）必须被摊平——摊平会有信息损失， 损失的那部分由队列记录与资产本身承担。
