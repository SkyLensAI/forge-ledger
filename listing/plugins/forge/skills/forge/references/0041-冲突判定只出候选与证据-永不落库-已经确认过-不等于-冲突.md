# 冲突判定只出候选与证据，永不落库；"已经确认过"不等于"冲突"

## 问题

S19 的形状是给定的：**只出候选 + 证据，不落库**。退一步看，这里有三个坑，
每一个都能让"冲突永远进队列"这句话在某一天悄悄失效：

1. **判定的输出是什么。** 如果判定函数顺手把冲突写进库里（或者返回一个
   "建议动作"让调用方应用），那么"谁有权改用户的状态"这个问题的答案，
   就变成了"任何能调到这个函数的地方"。而**冲突处理正是这个产品唯一能收费的动作**
   （implement2.md 把它标成未来的付费点）——把它做成语义判定函数的副作用，
   既毁掉信任，也毁掉商业模式。
2. **证据。** 一条"这两条互相矛盾"的记录，如果不带两侧各自的出处，
   人就无法核对它。而无法核对的冲突记录比没有更糟：它会训练人去点"知道了"。
3. **什么不算冲突。** 新证据说"数据库还是 SQLite"，而库里已有一条同样的 state——
   这不是冲突，是**再确认一次**。把这种情况报成冲突，队列会被正常的重复证据淹掉，
   而"队列里全是噪音"与"没有队列"在行为上是同一件事。
   这个仓库已经吃过一次同形状的教训：`evals/regressions/0003`——
   把"已经落盘过"与"被别人改过"当成同一件事，结果是一份落过一次的清单永久报假警。

## 考虑过的选项

1. **判定函数直接改库（或调用方拿到结果就应用）。** 最短路径，
   也最短地把"不许自动覆盖"这条纪律变成一句注释。implement1.md 反模式 6
   说的正是这件事。
2. **判定返回"冲突 + 建议动作"，由调用方自动应用低风险的那一档**
   （比如"同一条 state、同一个值"就直接刷新 `last_confirmed`）。
   看起来温和，但它定义了"低风险"这个口子——而口子会被扩大。
3. **判定只返回候选 + 证据，每一条都必须带两侧的 span，且必须能解析；
   不满足的整条丢弃（带理由），不进队列。** 应用只能在人 resolve 时发生（ADR-0028）。
4. **不做自动检测，只在人处理新候选时提示"好像有一条同题面的旧状态"。**
   那等于把队列的存在意义交给人的记性。

## 选定

**选 3。** 五条判据，逐条都有执行体：

1. **候选的形状里没有"应用"这一档。** `ConflictCandidate` 只有
   "两侧是什么、依据是什么、证据在哪"，没有任何可执行的东西。
   落盘与改写只存在于队列的 `resolve`（人触发的动作）里。
   自证：`missingAfterAdoption()` —— 采纳模型的提议之后，规则查到的那几条一条都不许少
   （模型只能加，不能减）。
2. **证据必须两侧齐全且可解析。** 每一条候选至少带一条来自"新证据"侧和
   一条来自"现有 state"侧的 span，全部要过 `parseSpan`。
   解析不到 → **丢弃整条候选并记账**，而不是"带着坏证据进队列"。
   理由与 ADR-0009 同源：腐烂的出处比没有出处更糟——它看起来像证据。
3. **归一化后完全相同 = 不是冲突。** 同一个题面、同样的内容，只是又被说了一遍——
   这是 `refresh`（再确认），进报告但不进队列。判据是**归一化后的字节相等**，
   不做语义比较：语义相似不构成本判据，"看起来像是同一个意思"正是要交给人的那部分。
4. **模型只能加，不能减。** 规则查到的冲突不受任何模型输出影响：
   模型的输出唯一的作用是**追加**候选（带 `basis: "model-proposed"`）。
   这条在类型层面成立——装配函数只接受两个数组并做并集，
   没有任何参数能表达"减掉一条"。
5. **只有 `state` 型实体会产生冲突。** `decision` 一旦 accepted 不可变（要改是新建
   supersedes，那是另一个决策，不是冲突），`event` 是发生过的事（不能被推翻），
   `rule` 靠 `origin_incident` 溯源。冲突是"**现在是什么样**发生了变化"这件事的名字。

**闸门里那条检查（Phase 5 的退出条件本身）**：拿一组合成的"新旧状态矛盾"跑完整路径，
要求三件事同时成立——**100% 进队列**、**每条的证据都能解析回仓库里的原文**、
**零条被自动应用**。前两条证明队列在工作，第三条证明它没有越权；
只有前两条时，一个"直接改写状态"的实现也能全绿。

## 后果

- **好**：`ConflictCandidate` 是纯数据，所以"冲突判定"能在没有文件系统、
  没有模型、没有 API key 的情况下测（`evals/golden/conflict/` 的合成集 + 探针）。
- **好**：队列里的每一条都可以被人逐条核对：两侧的 span 都能点开。
  这是"证据正确"从一句口号变成一条断言的地方。
- **好**：`refresh` 单列一档之后，队列的信噪比由**归一化相等**这条硬判据保着，
  不依赖检测器的调参。重复的证据不会制造工作。
- **代价**：保守的判据会漏掉"语义上矛盾但字面上不同"的对子
  （"存储层是 SQLite" vs "我们不再用嵌入式数据库了"）。
  漏掉的冲突不会进队列——它只能靠模型的追加提议碰上。
  已知缺口，写在 `docs/handbook/conflicts.md`，不假装它被解决了。
- **代价**：证据两条齐全的要求会让一部分真实的冲突被丢弃
  （现有 state 没有可解析的出处时）。这也是**有意的**：一条无法核对的冲突
  会污染人对整个队列的信任，而队列的信任是这个产品最贵的资产。
- **残余风险**：判据 3（归一化相等）对**措辞**敏感。同一件事被确认两次、
  第二次措辞不同（"用 node:sqlite" vs "用内置的 node:sqlite"），会被报成冲突，
  于是人多花一次判断。相比"漏报一次状态被推翻"，这个方向的代价小得多——
  但它确实会给队列带来需要人扫掉的噪音。
