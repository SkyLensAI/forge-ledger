# front-matter 带 `schema_version`，版本号就是分类法版本；迁移通道现在建、现在用

## 问题

S5 要定 front-matter，S7 要建迁移通道。front-matter 里要不要版本号？
如果要，它和 `taxonomy.yaml` 的 `version` 是一个东西还是两个？

## 考虑过的选项

1. **不放版本号**，靠"字段长什么样"猜版本（缺 `origin_incident` 即旧版……）。
2. **放 `schema_version`，与 `taxonomy.version` 分开编号**。
3. **放 `schema_version`，语义上就是分类法版本**：只有一个版本号。

## 选定

**选 3**，并且通道现在建、现在用。

- 两个版本号会立刻产生"哪个才是权威"的问题，而它们的取值必然在某些变更里不同步。
- 分类法版本**就是**资产格式版本：加类型、改必填字段、改状态词表，都是同一件事——
  资产格式变了。于是判定只需要比较一个数：
  `schema_version !== taxonomy.version` → `SCHEMA_VERSION_MISMATCH`（附修法：跑迁移通道）。
  不需要一张"字段 → 版本"的推测表——推测版本看着省事，实际在制造不可判定的边界，
  而且它永远会漏掉"只改了状态词表"这类变更。
- 通道先建，是排序原则 1（回填不了的东西先做）：**通道建好之前写入的数据，将来只能靠一次性脚本硬改**，
  而硬改脚本没有测试、没有版本区间、也没有"从哪迁到哪"的记录。
- 第一批被迁移的不是假数据：仓库里已有的 5 条 ADR 写在 schema 之前（没有 `schema_version`），
  `v0 → v1` 迁移的第一个真实任务就是把它们纳入版本纪律。
  **缺版本号 = v0**：这条规则让"还没迁移的旧资产"可判定，而不是让它们静默通过。

## 后果

- **好**：迁移是可测试的纯函数（`planMigration(from, to)` 返回区间列表；每个区间是一个纯变换）。
- **好**：区间缺口（有 0→1、没有 1→2）会明确报错，而不是"尽力而为地跳过去"。
- **好**：CI 对未迁移资产明确报红，不会"顺手兼容一下"——兼容分支是迁移债务的温床。
- **代价**：每次改资产格式都要写一段迁移 + bump 版本，即使当时库里是空的。
- **代价**：每个资产多背一个字段（一行）。
- **残余风险**：迁移只在被已有资产触发时才被真正验证。空库阶段的迁移是一段**没有数据可跑**的代码，
  所以 v0→v1 必须建立在真实存在的 v0 数据上——这 5 条 ADR 就是它的回归用例。
