# demo 只从自己的库生成

## 问题

implement2.md 给 S32 写的是一句很短、但很硬的话：

> 对外 demo = **你自己的库**，不是编造的样例。

为什么这句话值得一条 ADR：一个手写的 demo 可以展示任何你想要的效果，
但它不证明产品在你的真实数据上跑得通。编造的样例还会带来一个更隐蔽的问题：
**它不会腐烂**。真实的库会过期、会有孤儿、会有写了一半的替换；
样例永远干净。用样例做的 demo 在演示时最好看，也最不诚实。

## 考虑过的选项

1. **手写一个漂亮的样例站。** 否决。它展示的是编写者的设计能力，
   不是这个产品在真实资产上的输出；而且它会与真实库长期分叉。
2. **把 `docs/adr/` 手工整理成一组演示页面。** 否决。手工整理就是第二份真相：
   新增一条 ADR 后 demo 不会跟上，而"demo 少了一条"几乎不会被发现。
3. **用一条命令从资产库生成静态站，并在 CI 里检查它是否与库一致。** 采纳。

## 选定

- `forge demo --out <目录>`：
  - 输入只有资产（`--repo` 时是仓库自己的 ADR / 资产，否则是一个 vault）；
  - 输出 `index.html`、每条资产一页、`library.json`、`README.md`；
  - **没有样例数据入口**。这不是"暂时没做"：没有入口正是 S32 的执行体。
- 三条渲染纪律：
  - **HTML 转义**：标题、正文、出处都按文本处理。资产正文是人写的，也是模型写的；
    演示页不该成为执行库内容里的 `<script>` 的宿主。
  - **没有外部资源**：不引用 CDN、字体、脚本。直接打开 `index.html` 即可，
    两年后也不需要某个域名还在。
  - **逐字节确定**：没有时间戳、没有随机、排序键写死（R6 / ADR-0017）。
- `library.json` 的 `source` 字段写出 `repo` / `vault`：
  读者能分清"自举演示"与"真实用户库"，不需要靠猜。
- `E15_EVAL_BOOTSTRAP_DEGRADED` 检查：每条资产都有一页、demo 两次生成字节相同、
  `source === "repo"`、总数与库一致；`forge bootstrap` 还会把 `demo/`
  与库逐字节比对。
- Markdown 渲染器刻意很小：ADR 里实际出现的语法（标题、列表、代码、引用、链接）
  都支持；表格原样保留为 `pre`。渲染不了的语法**显示出来**，而不是悄悄丢掉——
  演示页上的缺失应该看得见。

## 后果

- **好**：对外 demo 与真实库是同一份数据的两份投影。新增一条 ADR、修一处出处，
  demo 重新生成就会跟上；忘了重新生成，`E15` 或 `forge bootstrap` 会报红。
- **好**：演示页能在离线环境打开。它不是营销页，是一份能被人翻的真实库。
- **代价**：页面比手写 demo 朴素。这个取舍是刻意的：S32 要的是**真实**，
  不是好看；而"好看"可以在真实数据上继续做，反过来不成立。
- **残余风险**：小型 Markdown 渲染器不覆盖全部 CommonMark；复杂表格会以
  原样文本出现。它保证的是"不丢内容、不乱执行"，不是"排版与 GitHub 一致"。
