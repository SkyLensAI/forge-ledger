# 多出口是投影，不是第二个真相；导出的 eval 不许自称"已确认"

## 问题

S24 要两个出口：**Skill 导出**与**Eval 导出**。三件事必须先定：

1. **出口是投影还是资产？** 如果 Skill 目录或导出的用例集进 `assets/`，
   下一轮 `forge lint` 就会把它们当资产来审，而它们没有出处、没有题面、不是人写的。
2. **Skill 出口会不会变成"预加载"？** 把一个 29 条 ADR 的库整个塞进 `SKILL.md`，
   正好违反 ADR-0029 那条"绝不预加载"——同一份库里两条出口互相打架。
3. **导出的 eval 能不能当黄金集用？** 它是机器从"事件 + 人确认过的资产"拼出来的。
   `E2_EVAL_GOLDEN_UNREVIEWED` 的判据是"有人确认过**这一份**"，
   而一份自动生成的用例集**不可能**满足它——这正是重点。

## 考虑过的选项

1. **出口产物进 `assets/`**（当成"特殊的资产"）。它会污染资产集合，
   让"约定即集合"（ADR-0012）失效：`assets/` 下每个 markdown 都必须是资产。
2. **Skill 只放规则与状态，决策全文另存**（`references/`）。`SKILL.md` 只放
   **每次都要知道的**，决策按需读——与检索那条纪律同构，只是一个在运行时、
   一个在打包时。
3. **导出的 eval 直接写进 `evals/golden/`**（省一步）。那会让 `E2` 直接变绿，
   而"确认"这个词从那一刻起就没有意义了。
4. **导出的 eval 写成 `proposed`，落在用户指定的输出目录里**，
   人要把它搬进 golden 目录就必须显式改 `review` 块。

## 选定

**选 2 + 4。** 三条：

1. **出口是投影，不是作者。** 每个出口都能从 `assets/` 重算，
   谁都不是"第二份真相"——所以它们住在 `index/` 那一侧的分类里（ADR-0015），
   不进 `assets/`。删掉重跑就是了。
2. **逐字节确定**（R6）：没有时钟、排序键显式写死、只有 `\n`、截断必须说出来。
   编号算法与 `emitAdrFiles` **同一套**（按 `(created, id)` 的位次），
   于是 `references/0003-…` 与 `adr/0003-…` 指的是同一条决策——
   两个出口给出两个编号会让"0003 是哪条"变成一个真问题。
3. **导出的 eval 永远 `review.status = "proposed"`**，而且把"为什么"写进文件本身：
   期望值来自**人确认过的资产**（它们的出处指着这些事件），
   而**没被覆盖的事件不构成负面期望**——那是"还没抽到"，不是"不该抽出来"。
   把前者当后者会让分数虚高，而虚高的分数比没有分数更危险。

导出的用例集因此可以被那把尺子**直接跑**：用例显式带 `source_id`
（golden 集里是省略的，由用例 ID 内容寻址推出来——导出时必须显式写下来，
否则"ID 推出 source_id、source_id 又来自 ID"会成一个环）。

## 后果

- **好**：三个出口（`AGENTS.md`/`adr/`、Skill、Eval）来自同一批资产，
  改一处不用改三处——它们都是 `emit` 的纯函数。
- **好**：Skill 出口的"不预加载"可判定：`SKILL.md` 里**不许出现决策正文**，
  正文只在 `references/` 里。这条被测试钉住（拿一段只该出现在 references 的正文去断言）。
- **好**：导出的用例集是"从真实 trace 反着造用例"的第一块拼图
  （implement1.md §3.4）——它的期望值不是标出来的，是**从库里长出来的**。
- **代价**：导出的用例集**暂时不是一把可用的尺子**：它要有人逐条读过去
  （`about` 与 `expected_why` 就是给这件事写的），改完 `review` 块才算黄金集。
  在那之前它只是一个**候选**——而这个状态是刻意的，不是没做完。
- **残余风险**：一份来源里"人确认过的资产"密度很低时，导出集的 `expected` 会接近空，
  于是它在尺子上表现为"精确率很高、召回率很低"。这不是缺陷，是**采集还没跟上**的读数。
