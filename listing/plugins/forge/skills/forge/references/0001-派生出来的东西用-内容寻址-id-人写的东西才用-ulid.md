# 派生出来的东西用**内容寻址** ID，人写的东西才用 ULID

## 问题

ADR-0007 定了 ID 的形状：`<前缀>_<26 位 Crockford base32>`，并选了 ULID 作为那 26 位。
Phase 2 的退出条件是**给一份脱敏会话导出，两次运行产出逐字节相同的 `AGENTS.md`**。
但 ULID 的后 80 位是随机段——同一份导出、同一台机器、跑两次，
会造出两个不同的 `event_` ID，于是两棵事件树、两份不同的 `AGENTS.md`。

这不是"ID 方案好不好看"的问题，而是 R6（产出必须逐字节确定）和 ADR-0007 直接对撞。
对撞点是：**ULID 的语义是"这个时刻被创建"，而派生数据根本没有"被创建"这回事。**

## 考虑过的选项

1. **给 ULID 的随机段喂固定种子**（比如进程级常量）。看起来最省事。
   但那是把随机性藏起来，不是消除它：换个进程、换个顺序，种子就变了。
2. **派生数据不用 ID**，只用内容哈希。ID 会变长、会带 `=`/大小写歧义，
   而且前缀丢掉了——`grep dec_` 和按前缀分区这两件事同时失效（ADR-0007 的立论基础）。
3. **形状不变（前缀 + 26 位 base32），但 26 位的取值分两种来源**：
   - 派生（连接器产出、可重算的）：`SHA-256(内容)` 的前 128 位编码成 26 字符；
   - 人工/模型产出（不可重算的）：真 ULID（48 位毫秒时间戳 + 80 位随机）。

## 选定

**选 3。**

- 判据只有一条：**这个 ID 指向的东西能不能重算出来。**
  能重算 → 内容寻址，因为它必须稳定；不能重算 → ULID，因为它需要一个"何时被写下"的语义。
  这条判据和 store 三层的判据是同一个（`sources`/`assets` 不可重算，`index` 可重算），
  不是巧合：它们都是"能不能重算"这一个问题的两种问法。
- 形状保持一致让 ADR-0007 的结论全部保留：前缀进 ID、`grep` 可用、按前缀分区、
  大小写归一、非法字符表（不含 I/L/O/U）。
- 内容寻址顺带解决了幂等：同一份导出导入两次得到同一个 `src_`，
  于是它派生的事件 ID 也稳定——**重复编译不产生新字节**，
  这正是"增量编译 + 内容哈希缓存"要的那件事。
- 派生 ID **不再承载时间**。这不是损失：事件的时序由 `occurred_at`（来自导出本身）承担，
  而"编译发生在几点"对消费者毫无价值，它只会让输出无法做快照。

## 后果

- **好**：Phase 2 的退出条件（两次运行逐字节相同）在架构上成立，而不是靠"别同时跑两次"。
- **好**：同一个事实从两台机器、两条路径导入，得到**同一个 ID**——跨设备可比、可去重。
- **代价**：派生 ID 按字典序排序不再等于按时间排序（ADR-0007 曾用这一点解释为什么选 ULID）。
  补偿：事件的排序键是 `occurred_at`，且 `event` 的排序在 emitter 里显式写着。
- **代价**：内容变一个字，ID 就变。对**不可变**的派生数据这是正确行为（改了就是另一条事件），
  但它意味着"编辑一条事件资产"等于"新建一条 + 旧的成为孤儿"——这是有意的摩擦。
- **残余风险**：`SHA-256` 的前 128 位在理论上可碰撞。对本产品（单机、万级资产）不是现实风险；
  真到了需要抗碰撞保证的规模，那是一次显式迁移，而不是现在为一个不存在的规模付复杂度。
