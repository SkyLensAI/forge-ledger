# 出处是「带 scheme 的 span」：判定是纯函数，IO 在边缘；不可解析与没有出处分开报

## 问题

"没有出处的断言不许入库"要变成代码。出处用什么形式写？谁来解析它？
CI 里没有用户的 `data/sources/`（`data/` 被 gitignore），那 CI 到底能校验什么？

**origin_incident（触发这条决策的真实问题）**：Phase 0 写的 5 条 ADR **是**带出处的，
但出处形如 `implement2.md#Phase 0 · 常见失败`——路径相对 `docs/`、锚点指向一个不存在的章节标题。
**出处写了，但没有任何东西能校验它**，于是"有出处"退化成了"有一段看起来像出处的文字"。
这个 incident 本身就是本 ADR 要解决的问题的最小样本。

## 考虑过的选项

1. **出处置为自由文本**（"来自 11 月 3 日的会话"）：人读得懂，机器判不了。
2. **出处置为 URL**：机器能判"是不是 URL"，但判不了"它是否还存在、是否指向那段话"。
3. **出处 = `scheme://target[#anchor]` 的 span**，anchor 限定为三种可机械判定的形式。

## 选定

**选 3。**

- 语法（v1）：scheme 只有两个——`file://`（仓库/工作区内文件）、`src://`（`data/sources/` 里的不可变片段）。
  anchor 三种：`#h:<标题>`、`#t:<原文片段>`、`#L<起>-L<止>`。
  匹配前把空白折叠成单个空格——这样文档里跨行的句子不会让 span 莫名其妙失效。
- **判定是纯函数，IO 在边缘**：`packages/core` 收到一个 `SpanIndex`（span → 事实：
  resolved / unresolved / unavailable）就出判定；读文件、建索引由边缘负责
  （闸门脚本、将来的 CLI / MCP server / 桌面端）。同一份判定因此可以在四种宿主里复用，
  并且可以用固定输入做快照测试。
- **"不可解析"与"没有出处"是两个码**（`PROV_SPAN_UNRESOLVED` / `PROV_NO_SOURCES`）：
  两者的修法不同（去修 span，还是去补证据），合并成一个码等于把修法也合并掉。
- **CI 只解析 `file://`**：`src://` 需要 source 层，那是 Phase 2 的 store。
  所以写进本仓库的资产必须用 `file://`——这不是限制，而是仓库的定位（宪法 + 自举资产，证据在 docs）。
  在 CI 里遇到 `src://` 报 `PROV_SCHEME_UNAVAILABLE`，**不静默放过**：
  "本闸门无法校验"和"校验通过"必须是两种不同的输出。
- **外部证据不进 span**：URL、工单、线上日志先落进 `sources/`（Phase 2 连接器）再用 `src://` 引用。
  "先存原件，再引用"是硬约束——否则出处会随外部世界腐烂，
  而**腐烂的出处比没有出处更糟**：它看起来像证据。

## 后果

- **好**：出处可校验，"每一行都能追溯到一个具体出过的问题"从口号变成红/绿。
- **好**：span 与存储无关，同一份资产可以在不同 vault、不同机器上重新解析。
- **代价**：写资产的人（以及 Phase 4 的模型）必须产出合法 span。模型产物一律先进候选区（S16），
  正是为了不让它直接写坏 span。
- **代价**：`#t:` 片段在目标文档被改写后会失效。**这是特性不是缺陷**（引用失效必须被看见），
  但它给文档维护加了一层义务：改掉被引用的句子 = 触发依赖它的资产复审。
- **残余风险**：`#t:` 只判定"目标里存在这段文字"，不判定位置唯一。
  同一句话在文档里出现两次时，span 指向的是"存在"而非"那一处"。
  真正需要精确定位的场景要等 `src://` + `#L` 区间与 source 层的字节偏移。
