store 三层是三条权限规则，由 API 形状强制，不靠自觉

问题

directory.md 给了三层（sources / assets / index），但"层"如果只是三个文件夹， 它就只是一个命名约定。Phase 2 要把它变成代码，于是必须先回答： 这三条规则里，哪一条是真正不可逆的？

答案是 sources：它存的是用户导出的原始字节，是整个系统里唯一不能重算的东西。 而最容易犯的错恰好是"顺手修一下"——比如为了加行号重新序列化一遍 JSON。

考虑过的选项

  1. 三个目录 + 文档里的约定（"请不要修改 sources"）。反模式 2 的标准形态。
  2. 运行时校验：写入时检查目标路径是否属于 sources/，是就拒绝。
  3. API 形状：sources 层没有提供修改/删除的函数，只有 import / list / read； 幂等靠内容寻址，写入靠 wx（已存在即失败）。
  4. 文件系统只读位（chmod 444）。跨平台行为不一致，且用户会自己 chmod 回来。

选定

选 3，并在真正不可逆的那一处再加一道运行时断言。

  • 选 2 的"运行时校验"是**把规则写成一句 if**：它仍然是一条可以被下一个人删掉的分支。 选 3 让"修改来源"在 API 层面不存在——不是"不要做"，是"没有那个函数"。 这是 R8 说的"把信任边界实现在代码里"的最小形态。
  • 内容寻址（ADR-0013）让"只写一次"不再是一个需要人记住的规矩： 同一份字节映射到同一个目录，wx 保证第二次写失败， meta.sha256 与当前字节不一致时抛错而不是覆盖—— 覆盖来源层是本系统最不可逆的动作，宁可炸掉。
  • index/ 的规则用同样的方式实现：这一层只有 rebuild()， 没有"更新某一行"。有了 update 就一定会有人把不可重建的东西塞进去， 然后"删掉能重建"这句话就不成立了。
  • assets/ 分成 writeDerived / writeAuthored 两个函数，而不是 write(doc, {overwrite})： 布尔参数在调用点读不出来，而这两种写入的错误后果完全不同 （派生写错 = 破坏幂等；人工写错 = 覆盖用户的东西）。

后果

  • 好：三条规则各有一个在调用点能读出来的执行体，而不是一段注释。
  • 好：--vault 下的目录布局与 directory.md 一致，但"层"的语义不依赖布局 （换 SQLite 存 sources 也不需要改判定）。
  • 代价：少了灵活性——想就地修一条来源必须走"新建一个来源"。 这是故意的：来源层的修改必须留下痕迹，而"就地改"不留下任何东西。
  • 代价：ensureVault 会创建 audit/ 空目录，而审计日志是 Phase 7 的事。 先建空目录是承认"它要有地方放"，但不要在报告里说审计已经做了。
  • 残余风险：sources/ 的只读是应用层的。用户直接 rm -rf sources/ 挡不住， 文件系统权限也没解决这个问题（选 4 被否）。真正的兜底是"内容寻址 + 可以从用户的导出重导"， 也就是说：来源层可丢，但不可改。
