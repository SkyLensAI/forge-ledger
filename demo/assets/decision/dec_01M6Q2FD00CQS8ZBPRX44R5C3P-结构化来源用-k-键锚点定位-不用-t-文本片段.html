结构化来源用 #k: 键锚点定位，不用 #t: 文本片段

问题

ADR-0009 给了三种锚点：#h: 标题、#t: 原文片段、#L: 行区间，并留了一句： "真正需要精确定位的场景要等 src:// + #L 区间与 source 层的字节偏移。"

Phase 2 的第一个来源是官方导出（JSON）。于是问题立刻具体化了： 一条事件要指回"导出文件里的那一条消息"，用哪种锚点？

  • #L: 要行号。JSON 的行号取决于序列化方式（缩进、键顺序）， 而来源层是原样的原始字节——我们不允许为了行号去重新序列化它（那就改写了证据）。
  • #t: 要一段原文。而 JSON 把引号、反斜杠、换行转义成 \" \\ \n： 同一句话在"原文"和"原始字节"里是两个不同的字符串。 更糟的是它会偶尔命中（标点少的句子转义后没变），于是失败模式是间歇性的。

考虑过的选项

  1. **用 #L: 行区间**：依赖序列化方式，等于把出处绑在"文件恰好怎么排版"上。
  2. **用 #t: 文本片段**：在 JSON 上因为转义而脆断，且失败是间歇的——最坏的失败模式。
  3. **只写 src://<来源 id>（不带锚点）：语法上合法（ADR-0009 允许省略锚点）， 能过闸门。但它等于说"这条断言来自那份文件"——在那份文件有 137 条消息时， 这不是证据，是看起来像证据**。
  4. **加第四种锚点 #k:<键路径>：指向来源里的一条记录，由连接器自己**解析。

选定

选 4。

  • 选 3 是这里最危险的一个，因为它能过闸门。ADR-0009 立论的全部理由是 "腐烂的出处比没有出处更糟"——一条无法定位的原文级引用正是这种腐烂： 它让人以为证据被保存了。
  • #k: 的判据分成两半，和 ADR-0009 的分工一致： 语法由纯函数判（键路径长什么样），命中由来源层判（那个键在不在）。
  • 命中判定复用连接器（connector.parse(text).records.some(r => r.key === key)）， 不写第二份实现。两份实现对同一份文件的判断必然漂移， 而漂移的方向永远是"校验那份更宽松"——R8 说的信任边界必须只有一份。
  • 键路径用语义键（conv_01/msg_03）而不是数组下标（conversations/0/messages/2）： 下标是"文件恰好怎么排"的投影，语义键是"这条消息是谁"的投影。 来源不可变，两者在 v0 都能解析；但语义键在人类排查时能直接读懂。
  • #k: 只对 src:// 有意义。file:// 上的 #k: 也实现了（按 JSON 键走）， 因为"指向工作区里某个 JSON 的某个字段"是同一个需求， 而让两种 scheme 支持不同的锚点集合只会制造特例。

后果

  • 好：出处从"整份文件"精确到"那一条消息"，闸门第一次能对导出类来源判红。
  • 好：连接器换了、来源重导了，只要键还在，引用就还在——引用绑定的是语义标识，不是排版。
  • 好：#k: 的错误信息可以很具体（"来源里没有键 conv_01/msg_03——它可能被改写过了"）， 而 #t: 命中不了时只能说"找不到片段"。
  • 代价：schema/provenance.md 与 ADR-0009 的锚点集合从 3 种变成 4 种， 两份文档 + 码表 + 测试要一起改（这正是 ADR-0010 要的那种有意的耦合）。
  • 代价：src:// 的 #h: / #t: / #L: 锚点在 v0 返回 unavailable 而不是硬猜： 它们要读原始字节并按文本匹配，而 v0 的来源层只保证"键存在"。明确记账，不假装支持。
  • 残余风险：键路径的稳定性是连接器作者的义务，不是代码能强制的。 一个用随机值当键的连接器会让所有引用在重导后失效——#k: 会把这件事暴露出来（判红）， 但拦不住它发生。等出现第二个连接器时，把"键必须来自导出内容"写进契约。
