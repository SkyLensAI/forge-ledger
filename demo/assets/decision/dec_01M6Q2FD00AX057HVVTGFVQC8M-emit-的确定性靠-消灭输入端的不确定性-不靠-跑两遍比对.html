emit 的确定性靠"消灭输入端的不确定性"，不靠"跑两遍比对"

问题

R6 要求产出逐字节确定，Phase 2 的退出条件把它具体成 "给一份脱敏会话导出，两次运行产出逐字节相同的 AGENTS.md"。

但"确定性"可以被做成两种完全不同的东西： 一种是事后检测（跑两遍 diff 一下，不同就报错）， 另一种是消除来源（让不确定性根本没有机会进入输出）。 前者是测试，后者是设计。选错了，测试会在某天变成"偶发失败"，然后被跳过。

考虑过的选项

  1. 只写一个"跑两遍比对"的测试。它证明的是"这次跑的两遍一样"， 对"下周会不会不一样"零保证。
  2. 输出前归一化：生成之后排序、剥掉时间戳再写。 但"剥掉时间戳"是事后补救——只要有人加了一个新字段，它就会漏。
  3. 在输入端逐条消灭：输出里出现的每一个值，要么是常量，要么是输入的纯函数； 排序键显式写死；不存在的值不留空档。

选定

选 3，并把"跑两遍"的测试当回归用例而不是判据。

  • 具体禁止的四类东西（与 R6 一一对应）：
  1. 时钟。没有生成时间、没有"最后更新"、没有文件名里的日期。 最隐蔽的一处是 ID：ULID 自带时间戳，所以派生 ID 改成了内容寻址（ADR-0013）。 这一条不改，退出条件在架构上就不成立。
  2. 随机数。派生 ID 同理；adr/ 的编号用"排序后的位次"，不用随机值也不用时间。
  3. 隐式顺序。凡是"可能多个"的地方都要显式排序键：资产按 (类型, ID)， 事件按 (occurred_at 降序, ID)，readdir 的结果一律先排序。 Object.keys 的顺序是插入顺序，而插入顺序来自代码路径——不是契约。
  4. 平台差异。换行只有 \n（.gitattributes 兜底，但 emit 不把正确性外包给 git 配置）； toLowerCase() 换成 ASCII 小写（土耳其语环境下 I 会变成 ı）。
  • 截断必须写进输出。事件时间线只放最近 20 条，但会打印"库中共 N 条"。 静默截断会让"最近 20 条"读起来像"一共 20 条"——那是在输出里撒谎， 比不确定更糟。
  • emit 是纯函数：输入是数据（资产 + 事件），输出是字节，没有 IO。 于是"确定性"可以被单元测试直接断言，而不是靠端到端跑两次去推断。
  • 端到端的"跑两遍"测试仍然要写，但它守的是别的东西： 它证明的是一条完整的路径（导入 → 编译 → 投影）里没有漏网的时钟。 它的角色是回归用例，不是判据本身。

后果

  • 好：确定性的来源是结构，不是纪律。新加一个字段时， "它必须来自输入"这条约束会立刻暴露问题（要么它来自输入，要么它根本不该在输出里）。
  • 好：emit 可以用固定输入做快照测试——这正是 Phase 3（S13）要的不变量之一。
  • 好：顺带得到可审计与可回滚：同样的输入必然产出同样的文件，diff 里只有真的变化。
  • 代价：输出里没有"生成于某时"这一行。人读的时候少了一个时间锚点。 补偿是内容本身（created / last_confirmed / occurred_at 都来自数据）。
  • 代价：所有"可能多个"的地方都得写排序键，比 for (const x of Object.values(...)) 啰嗦。
  • 残余风险：时区没有完全消除——created 是日期字符串，occurred_at 被归一成 UTC 秒。 如果将来某个连接器把"本地时间"当本地时间处理，输出就会随机器时区变。 缓解是 isoSecond 明确按 UTC 归一，但它拦不住一个不这么做的连接器； 等出现第一个这样的连接器时，把"时间戳必须归一成 UTC"写进连接器契约（棘轮）。
