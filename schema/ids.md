# ID 方案（人读的一半）

> 代码侧：`packages/schema/src/ids.ts`。ADR-0007 定了**形状**，ADR-0013 定了**取值来源**。
> 这份文档与那两处必须一致，漂移由一致性闸门判红（ADR-0010）。

## 形状

```
<前缀>_<26 位 Crockford base32>
```

- **前缀进 ID，不只进字段。** `grep -r "dec_"`、按前缀分区目录、日志里一眼看出是什么——
  这三件事都因此成立。类型信息放在两处比放在一处更难丢。
- **26 字符**固定长度：130 位（实际用 128 位，末尾补 2 个零位）。
  固定长度让正则和分区逻辑简单，而省下的几个字符没有任何人受益。
- **Crockford base32**：字符表是 `0123456789ABCDEFGHJKMNPQRSTVWXYZ`。
  刻意不含 `I` `L` `O` `U`——前三个和 `1` `0` 手抄时会混，`U` 整个排除是为了
  拼不出脏词。**解析时先归一化再比较**：`I`/`L` → `1`，`O` → `0`，大小写不敏感。
  不做这一步，`supersedes` 这类引用会因为手抄差异**静默断链**。

## 前缀表

| 前缀 | 含义 | 分区目录 | 备注 |
|---|---|---|---|
| `dec_` | decision（决策） | `assets/dec/` | accepted 之后不可变 |
| `state_` | state（状态） | `assets/state/` | 就地替换，必须带日期 |
| `event_` | event（事件） | `assets/event/` | 只追加 |
| `rule_` | rule（规则） | `assets/rule/` | 就地替换，必须绑 `origin_incident` |
| `src_` | 来源（**不是资产类型**） | `sources/src_…/` | 只读层，见 ADR-0015 |

前缀表本身住在 `schema/taxonomy.yaml` 的 `asset_types.*.prefix`，**不写在代码的注释里**：
类型和它的前缀必须一起改，两处维护必然漂移，而漂移的表现是
"分类法加了类型、ID 前缀忘了加"——一种只在真实数据上才暴露的错误。

## 取值来源：能重算的用内容寻址，不能重算的用 ULID

判据只有一条：**这个东西能不能重算出来。**

| | 能不能重算 | 取值 | 为什么 |
|---|---|---|---|
| `src_`（来源） | 不能（原始字节） | `SHA-256(原始字节)` 前 128 位 | 同一份导出重复导入必须命中同一个来源，否则事件会翻倍 |
| `event_`（事件） | 能（sources + 连接器） | `SHA-256(source_id + key + text)` | 两次运行必须得到同一个 ID，否则 AGENTS.md 逐字节相同这条退出条件在架构上不成立 |
| `dec_` / `state_` / `rule_` | 不能（含人的判断） | ULID（48 位毫秒 + 80 位随机） | 它们需要一个"何时被写下"的语义；时间可排序是白拿的便利 |

**派生 ID 里没有时间。** 这是有意的：时间戳进输出会让输出每次都不一样，
快照测试只能关掉，于是"确定性"就没有执行体了（R6）。事件的时序由
`occurred_at`（来自导出本身）承担，而"编译发生在几点"对消费者毫无价值。

## 已知代价

- 派生 ID 按字典序排序**不再等于**按时间排序（ADR-0007 曾用这一点解释为什么选 ULID）。
  补偿：事件的排序键是 `(occurred_at 降序, ID)`，在 emitter 里显式写着。
- 内容变一个字，内容寻址的 ID 就变。对**不可变**的派生数据这是正确行为，
  但它意味着"编辑一条事件"等于"新建一条 + 旧的成为孤儿"——这是有意的摩擦。
- ID 长（前缀 + 26 位），人读不如 `dec-7` 顺眼。这是为"可离线生成 + 可排序"付的价。
