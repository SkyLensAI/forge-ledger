# 0008 · 不存在的日历日期被静默归一成另一天

> 发现于补 `packages/ingest` 测试的时候。发现方式：一条断言
> "`2026-02-31T00:00:00Z` 应该被丢弃"红了——它没被丢，而是变成了 `2026-03-03T00:00:00Z`。

## 当初以为是什么

连接器里的 `isoSecond()` 用 `Number.isNaN(Date.parse(text))` 判"时间戳无法解析"。
注释里甚至写了这个反例：

> 形状对不代表日期存在（`2026-02-31T00:00:00Z`）。这一步是纯函数里的唯一一次日期解析。

也就是说，当初以为 `Date.parse` 会拒绝不存在的日期。

## 实际是什么

**`Date.parse` 会静默归一。** `2026-02-31` 不是"无法解析"，而是被折成 3 月 3 日
（非闰年的 `02-29` 同理）。于是：

- 一条页面上写着"2 月 31 日"的记录，会以 3 月 3 日的时刻进入事件 IR；
- 它不报错、不进 `skipped`，看起来和一条正常记录一样；
- 时间线因此被悄悄改写，而**改写证据正是采集层最不能做的事**。

## 怎么复现

```bash
node -e 'console.log(new Date("2026-02-31T00:00:00Z").toISOString())'
# 2026-03-03T00:00:00.000Z
```

## 留下了什么

1. `official-export.ts` 与 `web-capture.ts` 的 `isoSecond()` 都改成**往返校验**：
   - 带日期的字符串先按日历校验 `YYYY-MM-DD` 是否真实存在；
   - web-capture 是严格 UTC 秒精度，所以直接要求
     `new Date(parsed).toISOString().slice(0, 19) + "Z"` 与原文逐字节相同；
   - 不满足的返回 `null`，由连接器记进 `skipped`（不是静默丢）。
2. `evals/regressions/regressions.test.ts` 的 0008 同时钉住：
   - 闰日 `2024-02-29` 必须留下；
   - 非闰年的 `2026-02-29` 与 `2026-02-31` 必须被拒绝；
   - 走 `webCaptureConnector.parse()` 的真实路径再问一遍，坏日期必须进 `skipped`。
