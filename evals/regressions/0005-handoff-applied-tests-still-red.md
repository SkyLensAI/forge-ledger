# 0005 · "落盘之后这些测试就会转绿"——它们没有

> 发现于 Phase 6 动工前。发现方式：把 `handoff/` 的清单落盘、跑 `pnpm test`，
> 然后**对照 README 关于它们为什么红的说法**。

## 当初以为是什么

`README.md` 的验证状态一节写着（当时的事实）：

> 剩下 8 条是 Phase 5 的端到端用例，它们卡在**待人工落盘的那一项**上——
> 题面字段还没进 schema，所以资产渲染出来不带 `subject`，冲突判定自然看不到它。
> 落盘之后这 15 条会一起转绿——**这不是"应该会绿"，是"结构上只差那一个字段"**。

清单落盘了。跑 `pnpm test`：**仍然是红的**，只是红的地方换了三个。

## 实际是什么

三个失败各有各的原因，而且**都不在"待落盘"那一项上**：

1. `packages/core/test/emit.test.ts` 的 fixture 自己拼 `AssetFrontMatter`，
   加字段时它没跟着动。`renderAssetDocument` 读 `subject` 读到 `undefined`
   ——注意它**不是**报一条违规，是直接抛。
2. `evals/invariants/invariants.test.ts` 的 `seedVault` 造的 state 没有题面，
   于是"出处完整率 100%"这条不变量在一个**基线库本身就不合法**的前提下跑。
3. `apps/cli/test/conflicts.test.ts` 的"再确认不是冲突"——**这是一条真 bug**，
   与落盘无关：两侧的形状本来就不一样（资产带 `## 当前状态`，候选不带），
   归一化只折叠空白，于是"同一件事被再说一遍"被判成了内容不同。
   详见 ADR-0032。

## 为什么"结构上只差那一个字段"这句话是错的

那句话把一个**推断**写成了结论，而且写得比事实强（"这不是应该会绿"）。
推断本身不算离谱——`subject` 确实缺——但它漏了两件事：

- **加字段会波及所有手工拼 front-matter 的地方**（测试 fixture 就是拼得最多的地方）。
  这是"加一个字段"的固有成本，不是意外。
- **一条被更早的失败挡住的用例，它的失败原因是未知的**。
  它从没跑到过自己真正的那几行，所以"它为什么红"和"它为什么绿"都只是猜测。
  第 3 条 bug 就是这样藏了一整个阶段：它被 `subject` 挡在前面，
  而挡住它的那一项修好之后，它是红的，但原因已经是另一个了。

## 留下了什么

1. **三条一起修**：两个 fixture 补上 `subject`，一条判定剥掉模板标题（ADR-0032）。
2. **一条新用例**（`packages/core/test/conflict.test.ts`）：
   同一件事、两侧排版不同（一侧带 `##` 章节）→ 必须是 `refresh`，不是 `conflict`。
   这条用例的存在意义是"下次谁把归一化改回只折叠空白，它立刻红"。
3. **本记录**（R7 的那个"回归用例"位）。
4. **README 改成对照事实**：不再写"落盘之后就会绿"，改写成实测的条数与状态。

## 还没做什么（明确记账）

**没有一条闸门能拦住"把推断写成结论"这种错误。** 三个失败里有两个是 fixture 漏字段，
理论上可以由"类型检查覆盖全部构造点"拦住——但 fixture 是 `Partial<AssetFrontMatter>`
展开的，类型检查看不见。真正的缓解是**把"红了几条"写进 README 时必须同时写清
"红在哪一层的哪一件事上"**，而不是写一句"只差某个字段"。
这句话本身没法机器判定，所以它只能是一条写作纪律。记在这里，不假装它被解决了。
