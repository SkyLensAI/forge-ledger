# 0002 · 把多个来源的候选合起来判出处，每一条都被判成"编造"

> 发现于 Phase 4 写 `vault.extract()` 的时候。
> 发现方式：`apps/cli/test/extract.test.ts` 明明给了一条引用真事件的候选，
> 命令行却报告"候选区落盘 0 条"。

## 当初以为是什么

"守卫要用**这批候选当初的输入**去复核出处"——这句话我写对了，
但写成代码时是这么写的：

```ts
const guard = guardCandidates(
  { sourceId: "(全部来源)", events },     // ← 合并出来的假输入
  results.flatMap((result) => result.candidates),
  policy,
);
```

当时脑子里的模型是"守卫只是判出处，输入是谁不影响"。
`judgeCandidates` 里那一行 `parsed.span.target !== input.sourceId` 被我读成了
"来源 ID 对不对得上"的宽松检查，而不是"逐字节相等"。

## 实际是什么

`judgeCandidates` 对 `target` 判的是**逐字节相等**（ADR-0009 的既定行为）。
于是合并输入的 `sourceId = "(全部来源)"` 让**每一条**候选的出处都不匹配，
条条被判 `CAND_SPAN_NOT_IN_INPUT`。

**这个 bug 的症状是它最坏的地方**：不崩溃、不报错，
报告里每一条的理由都写得很有道理——

```
⚠ 丢弃 1 条（模型编造的内容 / 读不成的形状）：
  - [CAND_NO_SOURCES] #1：候选声明的每一条出处都指不回本次输入，重建之后一条不剩
⚠ 守卫拒绝 1 条：
  [CAND_SPAN_NOT_IN_INPUT] 一条真的决策：出处指向来源 src_TTP…，但这次抽取的输入是 (全部来源)
```

它看起来像"模型很会编"，而真凶在编排里。一个只看日志的人会去查模型调参，
而模型完全无辜。

还有一层：**它只在有多个来源时才暴露**。单个来源时，
`inputs.length === 1`，合并输入与真实输入只差一个 `sourceId` 字段——
那个字段还没进过任何人的眼睛。所以这个 bug 会在"用户导入了第二份导出"的那天，
突然让抽取全线失效。

## 怎么复现

```bash
# 现在是绿的（已修）；把 vault.ts 的 extract() 改回合并输入，它会立刻变红
node --test packages/store/test/extract.test.ts
```

用例：`多个来源：逐来源判出处，候选一条都不许被误判成编造`。
它用一台**看着题目回答**的模型（把请求里出现的每个事件键原样引回去），
所以"候选全被丢光"只可能来自编排，不可能来自模型。

## 留下了什么

1. **代码**：`extract()` 改成**逐来源判**（`units.map(unit => guardCandidates(unit.input, …))`），
   再用 `mergeGuards` 合并**已判定的结果**——而不是把候选合起来再判一遍。
2. **类型**：`ExtractionRun` 从 `{ inputs[], results[] }` 改成 `{ units[] }`，
   输入与产出**成对**存着。两个平行数组之间任何一处错位都会静默地把
   甲来源的候选对着乙来源的输入去判，而症状与上面一模一样。
   让错位在类型上不可能发生，比写一句"注意对齐"结实。
3. **代码注释**：`ExtractionUnit` 的注释里直接写了这件事的经过。
4. **本条记录**（R7 的那个"回归用例"位）。

## 还没做什么（明确记账）

`mergeGuards` 只是把三段结果拼起来。如果将来两段结果里出现**同一个候选**
（例如同一个来源被导入两次、内容寻址本该让它们成为一份，但如果连接器行为变了呢），
拼接会给出两条。当前由 `recordCandidates` 按候选 ID 去重兜住，
但那是**写入**那一层的事，报告层（`guard.inboxed.length`）会多算。
没有修，因为触发它的前提（同一来源产生两段输入）目前不可能——
`inputs()` 是按 `source_id` 分组的。
