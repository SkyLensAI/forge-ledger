# 0003 · "目标已被改动"与"这一项已经落盘过"被当成了同一件事

> 发现于 Phase 4 准备第二批 `handoff/` 的时候。
> 发现方式：核对上一批（Phase 3）到底落没落——清单说"待人工落盘"，
> 而 `scripts/gates/evals.mjs` 明明已经在仓库里，`pnpm test` 也是 130 条全绿。

## 当初以为是什么

`handoff/README.md` 写着"Phase 3 的产物在 `handoff/`，**由人执行**一条命令"，
而 `README.md` 的 Phase 3 表格写着 `S14 ⛔ 载体待人工落盘`。

两处都在说"还没落"。

## 实际是什么

**已经落了。** 逐项核对 sha256：清单里六项的**目标文件**全部等于**载荷文件**。
之所以看起来"还没落"，是因为：

1. `handoff/` 没有被删（它是"用完即删"的，而没人删）；
2. `README.md` 的状态行没跟着改。

而第二条之所以没被发现，是因为**脚本本身也分不清**：

```js
if (current !== entry.base_sha256) {
  problems.push("目标文件自基线以来已被改动——这份补丁是基于另一份文件写的，不能硬套");
}
```

"已经落盘"（`current === payload`）与"被别人改过"（既不是 base 也不是 payload）
都会落到这条分支上，于是 `node handoff/apply.mjs` 对一份**已经落完**的清单
永久报"目标文件自基线以来已被改动"，并拒绝执行。

那句提示会把人送去 diff 一个根本没有问题的文件。而下一个人看到它，
合理的反应是"这份清单坏了"或者"谁动过它"——两种反应都不会通向"它其实已经落完了"。

**一份说"还没做"的文档比一份说错了的文档更危险**：说错了会被纠正，
说"还没做"的只会让人不去看真实状态。

## 怎么复现

```bash
# 把某一项的基线指纹改成任意别的值（模拟"落过之后又被改"）
# 然后：
node handoff/apply.mjs
# 修复前：报"目标文件自基线以来已被改动"，退出码 1
# 修复后：报"已落盘"，退出码 0
```

## 留下了什么

1. **脚本**：每一项现在有四种状态——`pending` / `applied` / `conflict` / `missing`，
   只有后两种算问题。全部 `applied` 时打印"全部已落盘，无需动作"并退出 0。
2. **脚本**：`--verify` 的舞台改成"除载荷覆盖的目录外一律 junction 回工作区"。
   原来手列要复制的目录，第一次跑就漏了 `README.md`，
   于是 golden 用例 `ext-015` 的 span 解析不到、报 `E5_EVAL_GOLDEN_INVALID`。
   教训不是"要记得复制 README"，而是**手列清单一定会漏**——
   现在改成"根目录下的文件一律照抄"。
3. **文档**：`README.md` 的 Phase 3 状态行改回事实；`handoff/README.md` 里
   写明上一批已落盘、以及这次漂移的经过。
4. **本条记录**（R7 的那个"回归用例"位）。

## 还没做什么（明确记账）

`handoff/` 是不是"已经落完"没有进 CI 检查。它不该进：`handoff/` 不在版本控制里
（untracked），CI 上根本看不到它。所以这条性质只能靠"跑一下 `apply.mjs`"来查，
而它现在是**幂等且自解释的**——这是当前能做到的最好形态。
真正的修法是让这类"一次性产物"根本不需要人记着删，
但那要等 `handoff/` 出现第三次（现在是第二次）再说，理由同 ADR-0004。
