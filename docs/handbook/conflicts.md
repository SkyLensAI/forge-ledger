# Handbook · 归并与冲突怎么用（Phase 5）

> 这一页讲**怎么干活**：队列在哪、三种决议分别动了什么、出问题怎么收拾。
> 为什么这么设计在 `docs/adr/0025`–`0028` 里；判据在
> `packages/core/src/link.ts` / `conflict.ts`；队列的读写
> `packages/store/src/conflicts.ts`。

## 三十秒版本

```bash
forge link                      # 候选区 × 现有资产 → 归并 + 冲突判定 → 队列（不写 assets/）
forge conflicts                 # 看队列（每条都带两侧的证据 span）
forge conflicts --resolve <ID> --decision replace --date 2026-11-06 \
    --confidence 0.8 --rationale "确认过线上就是这个"   # ← 唯一会改写已有状态的动作
```

**一条纪律**：`forge link` 永远不改 `assets/`。要改，只有上面那条带 `--resolve` 的命令，
而且要你亲手给三个判断：决议、日期、理由。

## 一次状态替换长什么样

被推翻的那一代**不会消失**：

```
assets/state/state_01ABC….md   status: superseded   ← 正文与出处一个字节都没动
assets/state/state_01XYZ….md   status: active       ← 新的一代
                               supersedes: state_01ABC…
_conflicts/conf_….json         这条记录的完整经过（含替换前的快照）
```

三处合起来，才是一次替换的完整证据：**上一代说的是什么、这一代说的是什么、
以及当时凭什么信了新的**。`data/` 是用户的 home 目录（`directory.md` §五），
不是每个人的库都在 git 里——所以历史不能只指望 git。

**"当前状态"的口径是 `status: active` 的那一条。** 冲突判定自己也守这条：
被取代的那一代不再是"现在的事实"，否则同一次矛盾会在每一代旧状态上重复报一遍。

## 三种决议

| 决议 | 动了什么 | 什么时候用 |
|---|---|---|
| `replace` | 落下一代新状态（`supersedes` 旧的），旧那代只改 `status` | 新的确实对 |
| `keep` | **一个字节都不动** | 旧的仍然成立；队列记录里留下"你判过了" |
| `defer` | 不动，状态改成 `deferred` | 今天判不了（要问人、要等数据） |

三个都是**判决**，都会写进队列记录（谁、哪天、凭什么）。`keep` 与 `defer` 的区别
不是形式主义：前者是"我看过了，旧的没错"，后者是"我还没看明白"——
把它们合并成一档，队列里就再也分不出这两种状态。

`replace` 还会顺手把你的那条候选移出候选区：它已经变成资产了。

## 已知缺口（如实记账，不假装解决了）

**1. 同义题面会漏并、漏报冲突。** 题面键是**归一化后的字符串**（NFKC、折叠空白与
大小写、剥掉包裹标点），不做同义词。所以「索引层的存储后端」与「存储后端选型」
是两个实体，它们之间的矛盾不会被报出来（ADR-0026 的残余风险）。
缓解是模型提议那条路（题面不同但可能是同一件事 → 进队列），而它需要接上模型。

**2. 措辞敏感会带来噪音。** 同一件事被确认两次、第二次措辞不同
（「用 node:sqlite」vs「用内置的 node:sqlite」），会被报成冲突。方向是对的
（宁可多报一次，不可漏报一次状态被推翻），但队列里会有需要你扫掉的噪音。

**3. 一次替换写两个文件，而它们不是原子的。** 崩在中间会留下"两代都标着 active"。
下一次 `forge link` 会报出来：

```
⚠ 题面 state#索引层的存储后端 有 2 条 active 状态（…、…）：一次替换写了一半，
  或者有人手写了两条。修法是留一条 active。
```

修法就是那句：把该 `superseded` 的那条的 `status` 改回 `superseded`（或反过来）。
没有做事务——`data/` 是文件系统，事务会是这一层里唯一一个假装自己是数据库的东西。

**4. 题面塌陷是安静的。** 一个总给 `subject: "系统"` 的抽取器会让整个库变成一个实体，
于是每次确认都变成一次冲突。它不进 CI（那是抽取质量，归尺子），
所以 `forge link` 会把"题面最集中的前几条"打出来：

```
· 题面最集中的几条（**塌陷是这么开始的**，看一眼是不是抽坏了）：
  - 系统：12 条候选
```

## 队列文件（`_conflicts/*.json`）

- **ID 是内容寻址的**（`conf_` + `冲突键` 的哈希）：同一组矛盾重跑 `forge link`
  得到同一个文件，所以队列不会因为多跑了一次而长出第二条。
- **记录里有两侧的完整快照**：现状那侧的正文与出处、新证据那侧的值与候选 ID。
  "当时我们看到的是什么"必须留在记录里——否则事后无从复核。
- **没有时间戳**：时间进产出会让重跑产生 diff（R6）。"什么时候发现的"是审计层
  （Phase 7 / S27）的事。
- **记录一旦写下就不再改**，除了 `status` 与 `resolution` 两处。
  改它等于抹掉证据。
- **没有证据的记录读不进来**：`scan()` 会把它们报成 `invalid` 而不是静默跳过。
  一条没有证据的冲突记录，比没有更糟——它会训练人相信队列。

## 什么时候该担心

| 现象 | 含义 | 动作 |
|---|---|---|
| `forge link` 报"丢弃 N 条"里有 `没有可用的题面` | 那条 state 候选**不参与冲突判定** | 去补题面（ADR-0025）；这是最危险的一种安静 |
| `forge link` 报"丢弃 N 条"里有 `没有出处` | 有一侧的证据站不住 | 去补出处——核实不了的矛盾不许进队列 |
| 队列里 `basis=model-proposed` 的多 | 规则看不见的对子多（同义题面） | 正常，但值得看一眼是不是题面写得太散 |
| `forge conflicts` 列出 `invalid` | 有人手改过队列文件，或写坏了 | 打开那个文件看；它是 JSON，不静默跳过是**故意的** |
