# Handbook · 维护机器怎么用（Phase 7 · S25–S28）

这个库的敌人不是"抽得不准"，是**烂得没有声音**：一条状态过期了、一次替换写了一半、
有人绕过工具往目录里放了个文件。这三件事在读的时候都长得跟正常一样。
Phase 7 的四件东西全是冲这个去的。

排序与判据来自 implement2.md 的 P7：**linter、定时任务、审计、周报**。

## 一、健康检查（S25）

```bash
forge health --today 2026-11-06              # 整份报告
forge health --today 2026-11-06 --due        # 只问"今天该找谁确认"
forge health --today 2026-11-06 --out health.md
```

**它只读。** 跑一百遍也不会改你库里的一个字节——这条由测试和探针各钉一遍
（探针拿本仓库自己的资产跑一遍，然后比对目录树的字节）。

四类腐烂，各自的形状与"为什么它是静默的"：

| 码 | 形状 | 为什么你平时看不见 |
|---|---|---|
| `HEALTH_ORPHAN` | 一条资产没有任何邻居 | 它照样被检索到，只是没人会再碰它 |
| `HEALTH_INDEX_DRIFT` | `index/` 与 sources + assets 对不上 | 读它的人会拿到旧的答案，而旧答案与正确答案长得一样 |
| `FRESHNESS_EXPIRED` | `state` 超过窗口没确认 | 过期的状态读起来与新鲜的一模一样 |
| `HEALTH_SILENT_SUPERSESSION` | `supersedes` 链断了，或同一题面多条 `active` | 冲突判定只在新候选到来时看那个题面 |

**孤儿是 `info`，不进退出码**；其余四类进。这个区分是有意的：一条长期挂着的红
等于没有红，而报告的全部价值就是"红的时候有人信"。

### 为什么没有"健康分"

你可能会想要一个 0–100 的数字。这里刻意没有，理由是那个数字会改变行为的方向：
有了分数，"哪件事该被处理"就变成"怎么把分数弄回去"，而**最省事的提分方式是
删掉报错的那几条**。所以报告里只有清单、计数，和"先做这三件"。

## 二、新鲜度任务（S26）

**定时任务只能问，不能自己答。** 这是这一节唯一重要的一句话。

```bash
# 每天问一次：有没有到期的 state？
forge health --today "$(date +%F)" --due
```

有到期的事就**非零退出**——cron / 计划任务只在需要你动手时来敲门。
这就是"定时任务"与"每周一封没人看的邮件"的区别。

回答它的是**人**：

```bash
forge confirm state_01M6Q… --date 2026-11-20 --note "又问了一遍，索引层仍然是 node:sqlite"
```

`confirm` 只动 `last_confirmed` **一个字段**：正文、出处、题面一个字节都不动
（这一点由一个自证函数保证：写别的东西就拒绝落盘）。`--note` 必填，
而它**进审计、不进资产**——资产里躺着一段"为什么我认为它成立"，
会让下一个读它的人分不清哪句是事实、哪句是当时的辩解。

调度配方（挑一个）：

```cron
# crontab -e —— 每个工作日早上 9 点问一次；有到期的事才会吵你
0 9 * * 1-5  cd ~/forge && forge health --today "$(date +\%F)" --due
```

Windows 计划任务 / launchd / 公司里的调度平台同理：**一条命令，看退出码**。

> **为什么不让任务自动刷新 `last_confirmed`？** 因为那会让库永远看起来是新鲜的。
> 一年之后你的库里全是"30 天内确认过"的状态，而其中大部分你从来没再看过一眼——
> 维护机器把唯一有价值的那个信号自己抹掉了。
> `forge` 里**没有** `--auto-confirm` 这个开关，这不是"还没做"。

## 三、审计（S27）

```bash
forge audit                     # 最近 20 条
forge audit --limit 100         # 更多
forge audit --verify            # 核对哈希链（链断了就非零退出）
```

日志在 `<vault>/audit/audit.jsonl`，一行一条：

```json
{"actor":"allentire","at":"2026-11-06T13:09:43.246Z","detail":{...},"hash":"…","kind":"asset-promoted","prev":"…","seq":2,"subject":"state_01M6Q…"}
```

**它记的是经过 forge 的每一次写入**：来源导入、模型抽出的候选、人工确认（`promote`）、
冲突判决（`resolve`）、重新确认（`confirm`）。派生的写入（重编译的索引层）不记——
**被刷屏的日志等于没有日志**。

### 它是怎么被强制的

不是"记得写"。`@forge/store` 里只有**一个**写资产的入口：

```ts
writeAuthored(doc, draft)   // 第二个参数是审计条目：谁写的、什么时候、凭什么
```

第二个参数**不是可选的**，而且运行时还会再问一遍（类型不是边界：`any`、
从 JS 调过来都能绕过去）。给不出见证人，代码就拒绝落盘。探针每次 CI 都试一遍
"不给见证人直接写"，要求它抛。

### 它的边界（明确记账）

- **它挡不住直接改文件系统。** 任何人都可以往 `assets/` 里放一个 markdown，
  文件系统不会问他"你记了吗"。所以审计不可能"强制每一次写入"——
  它能做的是让这种**沉默的写入在健康检查里被看见**（`AUDIT_UNATTRIBUTED_ASSET`）。
  这是记账，不是假装堵住了。
- **同时写没有锁。** 两个进程同时对同一个库跑 `promote`，
  两边会读到同一个链尾。链的验证会把它报出来，但**不会**阻止它发生。
  单人本地工具里可以接受；团队版（Phase 8）要在这里加文件锁。
- **链断了之后，整份日志都不再可信**——包括那些看起来没问题的条目。
  修法是恢复备份、或者把"这一段不可追溯"写下来。**不要**手工调 `seq` 或重算 `hash`：
  那是改历史，不是修审计。

## 四、周报（S28）

```bash
forge weekly --today 2026-11-06              # 窗口默认 7 天
forge weekly --today 2026-11-06 --days 30 --out weekly.md
```

周报与健康报告的分工是**差异 vs. 快照**：

| 一节 | 数据从哪来 | 它回答的问题 |
|---|---|---|
| 这一周库变成了什么样 | 健康检查 | 现在有多少条、有多少条过期 |
| 这一周谁动了库 | 审计日志 | 这一周有没有过写入、谁做的、改了什么 |
| 需要你回答的问题 | 到期清单 | 今天该确认哪几条 |

窗口与基准日都是**输入**，所以同一周的周报可以重印，字节相同（R6）——
于是它可以进邮件、可以 diff、可以贴进 issue。

**没有审计日志时，周报不会说"这一周很安静"**：那两句话不一样。
把"没有账本"渲染成"什么都没发生"，就是用一份空报告替缺失的账本背书。

## 五、规模：那个 500–1000 的坎

implement2.md 给 P7 写的退出条件是"库里涨到 500–1000 条事实仍然可用"。
**这一行会一直写着"未达成"**——它是一条关于人的判据，代码证明不了。
代码能证明的是三件相关的事，它们每次 CI 都跑（`E14`）：

1. 1000 条语料下，同一份输入两次产出的字节相同（确定性不随规模退化）；
2. 埋在 1000 条里的**一处**腐烂（"替换写了一半"）仍然被找到（信号不被淹）；
3. 健康检查在 1000 条上仍然分得开干净语料（零发现）。

这三条不成立时，"还能用"这句话连地基都没有。但它们成立**不等于**库好用。

## 六、日常怎么用

| 什么时候 | 跑什么 |
|---|---|
| 每次改完库 | `forge compile`（让索引层跟上）+ `forge lint --today $(date +%F)` |
| 每周一次 | `forge health --today $(date +%F)` → 看"先做这三件" |
| 有人问"这条是什么时候定的" | `forge audit --limit 50` |
| 想确认审计没被人动过 | `forge audit --verify` |
| 要给别人看这个库的状态 | `forge weekly --today $(date +%F) --out weekly.md` |

## 已知缺口（不假装它们被解决了）

- **审计的边界是文件系统**（见上）。直接改 `assets/` 的写入只能被"下一次健康检查"发现。
- **孤儿判定只覆盖 `decision` / `state` / `rule`**，而且孤儿是 `info`。
  一个长期没人碰的库会积累几百条孤儿，报告里会有"共 N 处"那一行——
  它是信号，不是待办清单。
- **周报的"这一周"是自然日窗口**，不是"上次周报到现在"。补发、跳过一周，
  窗口会重叠或留空——这两种情况报告里看得出来（窗口写在标题上），但不会被纠正。
- **`forge audit` 没有过滤条件**（按 actor / kind / 时间）。日志长了之后会难用，
  而"难用的审计"与"没有审计"在实际效果上差不多。补它的判据是：出现真实的用法需求。
