# 冲突处理：新建一代状态 + `supersedes` 链，由人给理由；不就地覆盖

## 问题

人在队列里点"新的对"之后，落盘要动**已有的资产**。这一动有三条互相拉扯的约束：

1. **`state` 的写规则是"就地替换，必须带日期"**（`schema/taxonomy.yaml`）。
   "就地"的意思是：一个问题只有一条当前答案，不许两条并存——
   否则"现在是什么样"变成一个需要检索和比较的问题。
2. **不许静默覆盖。** 用户的库未必在版本控制里：`data/` 是用户的 home 目录
   （`directory.md` §五），不是每个人的 `~/.forge/` 都有 git。
   就地覆盖会让被推翻的那一代**只剩一份**，而且是在冲突记录里，不是在库里。
3. **判定的责任要能被指认。** 一次状态替换改变了用户库里的"事实"。
   如果记录里只有"新的赢了"，下一个读它的人没法回答"当时为什么信新的"。

## 考虑过的选项

1. **就地覆盖旧文件**：把新内容写进同一个 `state_*.md`，更新 `last_confirmed`。
   最贴合 `replace_in_place` 的字面意思，也只有一条文件。
   代价是旧内容在库里消失（没有 git 就没有第二份），而且 `supersedes` /
   不变量 2（新状态不早于旧状态的确认日）那套机制全部用不上。
2. **新建一代 + `supersedes` 链**：新 `state_*.md`（`supersedes: <旧 id>`），
   旧的那条把 `status` 改成 `superseded`。
   两代都在库里、可 diff、可回滚；"就地"在**实体**层面成立
   （一个题面只有一条 `active`）。
3. **两条都留但都不改状态**，靠时间戳排序决定谁是"当前"。
   那等于把"当前状态"变成一个每次读取都要算的查询——而"过期的事实比没有事实更糟"
   这条失败模式，正是从"当前状态需要推断"开始的。
4. **根本不动资产**：把决定只写在队列记录里（"采纳新的"），下次编译时再合成。
   于是资产不再是事实的唯一真相，而编译多出一条只有某个阶段才跑得到的路径。

## 选定

**选 2**，并且把那次替换的**两个日期**都强制带上：

- **新资产** `created` = `last_confirmed` = 人给的那个日期（**必填，没有默认值**）。
  与 `forge inbox --promote` 同一条理由：值得记的是"人确认它的那天"，
  不是命令跑的那天；而默认值会让"确认"退化成一次点击。
- **旧资产只改 `status: superseded`**，正文与 `sources` 一个字节都不动。
  于是一代状态被推翻之后仍然可读、可核对——这是"不许静默覆盖"在结构上的兑现。
- **`supersedes` 必须同时指向旧的那条，且旧的必须存在**。
  这条链不是装饰：不变量 2 会检查"新状态的 `created` 不早于旧状态的
  `last_confirmed`"，于是"新状态从过去就开始生效"这类时间线错误会被抓到
  （`evals/invariants/invariants.test.ts`）。
- **`rationale` 必填**（和 `confidence` 一样，没有默认值）。
  队列里那条记录同时留下**替换前的完整快照**（旧 id、旧正文、旧出处、旧状态），
  于是"当时为什么信新的"这个问题在记录里就有答案，而不用去挖历史。
- **三种决定，语义各自独立**：`replace`（新的对，落盘）、
  `keep`（旧的仍然成立，**不写任何资产**）、`defer`（今天不判，留在队列里）。
  三者的区别是"动了什么"，所以它们必须是三档，而不是一个布尔值。

**这一条是 Phase 5 的 CI 强制项**（implement2.md 的 P5 行写的是"无自动覆盖"）：
队列是**唯一**能改 `assets/` 的冲突通路，而它只接受人的显式决定。
闸门每次 CI 都跑一遍合成集，要求"零条被自动应用"。

## 后果

- **好**：状态的历史留在库里，不在某个日志里。用户回滚一次误判，
  只需要把 `superseded` 改回 `active`——不需要找到备份。
- **好**：`replace` 的三个输入（决议、日期、理由）全是人的判断，
  而它们都进了队列记录：**"谁在什么时候凭什么把这条状态换掉了"** 有答案。
  这是将来团队版与审计层（Phase 7 / S27）的接口。
- **好**：`keep` 与 `defer` 都不写资产，所以队列可以是"看一遍什么都不改"的地方——
  一个必须有产出的队列，会训练人乱点。
- **代价**：`state` 的条数会随替换次数增长，而 `last_confirmed` 只挂在最新那代上。
  查询"当前状态"必须过滤 `status: active`。这条口径写在
  `docs/handbook/conflicts.md` 里，并且由冲突检测**自己遵守**
  （它只把 `active` 的那条当作"现有的旧状态"——否则每一代旧状态都会重复报一次冲突）。
- **代价**：一次替换要写两个文件（新资产 + 旧资产的 status），而它们不是原子的。
  写了一半的后果是"两代都标着 active"，下一次 `forge link` 会把它当成
  "同一个题面有两条 active"报出来（`docs/handbook/conflicts.md` 里写明怎么修）。
  没有做事务：`data/` 是文件系统，事务会是这一层里唯一一个假装自己是数据库的东西。
- **残余风险**：`rationale` 是自由文本，所以"写了理由"不等于"理由成立"。
  与所有评审类机制一样（ADR-0020 的残余风险同款），它降低"没想就点"的概率，
  不保证"想过"。
- **残余风险**：不变量 2 只检查日期与链路，不检查"新的内容是否真的比旧的更接近事实"。
  那件事没有任何机器判据——它是人的判断，而这个设计把它放在人手里的方式是
  **让证据必须两侧齐全、可点开**（ADR-0027），而不是让它自动发生。
