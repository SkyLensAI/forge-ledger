# 浏览器的脆弱性前移成一份可热更新的配置；判定一律不进扩展

## 问题

S23 的两句话是"只做**取用 + 增量采集**"与"**选择器配置可远端热更新**"。
把它们落在代码里时，有三件事必须先定，否则这个出口要么是个空壳，要么是个洞：

1. **脆弱性是结构性的。** 这个品类的第一大差评是"平台一改版工具就坏"（占全部评价 16%），
   而插件是所有来源里最脆弱的一环：它依赖 DOM，DOM 是私有实现细节。
   所以顺序才是"先做官方导出（平台承诺过的接口），插件放到 Phase 6"。
   脆弱性消不掉，只能**前移**：DOM 改版时要改的是**一份配置**，
   不是一次扩展发版（发版要过商店审核，那是几天到几周）。
2. **远端配置是一个执行面。** "远端可热更新"如果等于"远端可以下发代码"，
   那就等于"远端可以改你的浏览器"。
3. **浏览器执行不了本仓库的 TypeScript。** 本仓库零构建（ADR-0011 靠 Node 的原生类型擦除），
   而浏览器没有类型擦除。于是扩展**没法** import `@forge/core`——
   这直接决定了判定该住在哪。

## 考虑过的选项

1. **把判定在扩展里用 JS 抄一份。** 便宜，但从此有两份实现，
   而漂移的方向永远是**浏览器那份更宽松**（R5 反对的就是这件事）。
2. **给扩展加一个打包步骤**（tsc 或 esbuild）。它打破了"零构建"，
   而且不解决根本问题：`@forge/core` 依赖 `node:crypto` 与 zod，
   打进浏览器要么引入一堆 polyfill，要么再切一层包。
3. **判定全部留在本机桥（`forge serve`）**，扩展只做"读 DOM、发请求"。
   扩展里没有一行"到底算不算"，引擎仍然是那一份、那份被测试的。
4. **不做扩展**，只做 MCP。那等于放弃"取用发生在你正在读的页面里"这个场景。

## 选定

**选 3。** 于是这条流水线是：

```
页面 ──(DOM 胶水: 选择器取值 + 相对时间折 ISO)──▶ 扩展
                                                      │ POST /capture（原文，无键）
                                                      ▼
                              forge serve（127.0.0.1 + token）
                                                      │ 判定全在这里
                              packages/core/src/selectors.ts
                                                      │ 算键 / 去重 / 组载荷
                                                      ▼
                                              sources/（只追加）
```

**四条判据**：

1. **远端配置里没有代码。** `SelectorConfig` 只有字符串：`match`、`item`、`fields.*`。
   解析器不 `eval`、不 `new Function`。所以"配置被投毒"的最坏后果是**采不到东西**，
   不是"能在页面里跑任意代码"。**这条性质是热更新敢做的前提**，
   而且它被测试钉住（扩展的每一个 JS 文件都不许出现动态执行）。
2. **热更新的方向是确定的**：`revision` 大的赢，**相同则远端赢**。
   相同也让远端赢，是因为本地那份只是"随包发的兜底"，而远端那份是活的——
   反过来会让一次扩展更新**把远端的热修倒退回去**，而倒退是无声的：
   选择器还在，采到的东西变少了。
3. **键由桥派生**，不由浏览器算。浏览器只报原文；`captureKeyOf`（内容寻址）
   与"已经采过的"判定都在桥这一侧，判据是**已有的 sources**（重新解析一遍），
   而不是一份会漂移的本地集合——存一份的结局是有人手删了来源之后，
   同一条被采第二次，而"库里多一条重复记录"比多花几十毫秒难查得多。
4. **桥只绑回环、要 token、网页来源一律 403。** 回环不等于安全：
   任何一个网页都能向 `http://127.0.0.1:8787` 发请求。没有 token 的话，
   你在浏览器里打开的任何页面都能读走你整个库。CORS 只回显扩展来源——
   token 可能被截屏、被贴进聊天记录，所以两道门都要有。

## 后果

- **好**：扩展里没有判定，"两份实现漂移"这件事在结构上不会发生。
  唯一成文的重复是 `apps/extension/src/match.js` 的"最长前缀赢"（页面侧必须知道
  当前 tab 归谁管），而它被**逐条比对**测试钉住：拿一张 URL 表，
  让它的输出与 core 的 `hostForUrl` 一致。漂移的那一刻测试就红。
- **好**：`forge serve` 与 MCP 是两个宿主，但走的是同一份判定
  （`vault.context()` / `vault.capture()`），所以"命令行看到的和扩展看到的
  不一样"不可能发生——两边都由测试逐字节断言与 CLI 相同。
- **代价**：**扩展本身没有任何自动化验证**。CI 里没有浏览器，
  那几十行 DOM 胶水测不了；能测的只有它的**结构**（清单指向的文件存在、
  语法合法、没有 import 工作区、随包的配置能被 core 解析）。
  这与 `model-http.ts` 没被真实端点测过是同一类记账，写在
  `apps/extension/README.md` 的「没做什么」里。
- **代价**：多一个常驻进程。它换来的是"判定只有一份"，而那条正是 R5。
- **残余风险**：`selectors.default.json` 里的三条选择器是**示例，不是维护过的配置**。
  真正被维护的是远端那一份——这也正是它可热更新的理由。
